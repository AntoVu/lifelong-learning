Processes and system calls

Your laptop is running hundreds of programs at once, on a handful of CPU cores, and none of them can read another's memory or crash the machine. That's the operating system's work. This stage looks at how it does it, starting with its most basic idea: the process.

    What an operating system does

    The free OSTEP textbook, used in many university OS courses, sums up an operating system as three jobs:

    • Virtualization: give each program the illusion of its own CPU and its own memory, even though they all share one machine.
    • Concurrency: let many things happen at once, safely.
    • Persistence: keep data on disk, organized into files, across crashes and reboots.

    The core of the OS, the kernel, runs with special privileges. The CPU itself enforces two modes: in kernel mode, code can touch any memory and talk to hardware; in user mode, where your programs run, it can't. Any attempt to do something privileged from user mode, like reading another program's memory, triggers a fault that hands control to the kernel, which usually ends the offending program.

    The process

    A process is a running program: its own address space (the code, heap, and stack from stage 4), its register values including the program counter, and the resources the OS is tracking for it, like open files. Each has a number, its process ID (PID). Run the same program twice and you get two processes with separate memory.

    Check

    A process calls read() on a file that has to come from disk. What state is it in while it waits?

    Blocked. A disk read takes thousands to millions of CPU ticks (stage 4), so the OS runs other processes in the meantime and moves this one back to Ready when the data arrives.

    System calls

    If user-mode programs can't touch hardware, how does a program read a file, print, or open a network connection? It asks the kernel, through a system call. The program puts a call number and arguments in registers and runs a special instruction (syscall on x86-64). The CPU switches to kernel mode and jumps to the kernel's handler, which checks the request, does the work, and returns to user mode with the result.

    Linux has a few hundred system calls: open, read, write, close, fork, execve, mmap, and so on. Python's open() and print() end up as these calls, made for you by the C library. The tool strace shows every system call a program makes, and it's one of the best debugging tools on Linux.

    Check

    Why can't a normal program just read the disk directly, without a system call?

    Protection. If any program could talk to the disk, file permissions would mean nothing. The hardware's user and kernel modes, plus the system call doorway, let the kernel check every request.

    fork, exec, and wait

    Unix creates processes in two steps, and Linux and macOS still work this way:

    • fork() makes an almost exact copy of the calling process. Both continue from the same line. The only difference is what fork returns: the child's PID in the parent, and 0 in the child.
    • exec() replaces the current process's program with a different one, keeping the same PID.
    • wait() makes a parent sleep until a child finishes.
    import os

pid = os.fork()                  # one process goes in, two come out
if pid == 0:
    print("child: my pid is", os.getpid(), flush=True)
    os._exit(0)
else:
    os.waitpid(pid, 0)           # wait for the child to finish
    print("parent: my child was", pid)

    (The flush=True matters. Without it, the child's output can sit in a buffer and vanish when os._exit ends the process: an actual bug found while testing this example.) A shell is this loop: read a command, fork, have the child exec the command, and have the parent wait for it. Splitting creation into two steps lets the child set things up in between, such as redirecting its output to a file for ls > out.txt.

    Practice 1

    A program calls fork() three times in a row, with no ifs. How many processes exist afterward, including the original?

    HintEach fork doubles every process that reaches it. Step through the panel.

    2 × 2 × 2 = 8. With n forks in a row, 2ⁿ processes. That doubling is also what makes a fork bomb so dangerous (see below).

    Check

    What does fork() return in the child process?

    0. That's how the two copies tell themselves apart: same code, different return value, so if pid == 0 sends them down different paths.

    Practice 2

    How many lines does os.fork(); os.fork(); print("hello") print?

    HintCount the processes that reach the print.

    4: two forks make four processes, and every one runs the print.

    Switching between processes

    With hundreds of processes and a few cores, the OS has to take turns. A hardware timer interrupts the CPU every few milliseconds and hands control to the kernel. The kernel saves the running process's registers (including its program counter) into memory, picks another process, loads that one's saved registers, and returns to it. This is a context switch. It happens so often, hundreds of times a second per core, that every program seems to run continuously. Which process goes next is the scheduler's decision, and that's the next lesson.

    Processes can also be poked from outside with signals. Pressing Ctrl+C sends SIGINT, which by default ends the program; kill sends others.

    Check

    You type ls in a terminal. Which sequence does the shell use to run it?

    fork, exec, wait. The shell survives because only its child was replaced by ls. Add & to a command and the shell skips the wait, running it in the background.

    When this goes wrong

    The fork bomb

    This line of Bash is famous: :(){ :|:& };:. It defines a function named : that runs two copies of itself, piped together, in the background, then calls it. Each copy does the same, so the number of processes doubles again and again, exactly like the panel, but forever. Within seconds the system's process table fills up, and the machine can't even start the program you'd use to stop it. Nothing about it is a bug in the OS; it just uses fork as designed. The defense is limits: Linux can cap the number of processes per user (ulimit -u) or per group of processes (the pids controller in cgroups), which is one of the protections containers rely on.

    What to remember

    • The OS virtualizes the CPU and memory, manages concurrency, and persists data. Its kernel runs in a privileged mode.
    • A process is a running program: address space, registers, and OS resources. It's running, ready, or blocked.
    • Programs reach hardware only through system calls, which switch the CPU into kernel mode.
    • fork copies a process (returning 0 in the child), exec replaces its program, wait waits for a child. Shells are built on these.
    • A timer interrupt and context switches let one core take turns among many processes.
