Sequences

Lists, tuples, strings, and ranges are all sequences: ordered collections you can measure, index, and loop over. Learn the operations once and they work on all of them.

s = "abcdef"
len(s)          # 6
s[0], s[-1]     # 'a', 'f'        negative indexes count from the end
s[1:4]          # 'bcd'           a slice: start included, stop excluded, like range
s[::2]          # 'ace'           every second item
"cd" in s       # True
for ch in s: ...

The differences are about change. A list is mutable: you can append, remove, and assign to items. A tuple is an immutable list, written with parentheses: (3, 4). A string is an immutable sequence of characters. Use a tuple for a fixed group of values that belong together, like a coordinate, and a list for a collection that grows.

Practice 1

What is "abcdef"[1:4]?

HintIndexes start at 0. The slice includes index 1 and stops before index 4.

'bcd': indexes 1, 2, and 3. The length of a slice is always stop − start, here 3.

Practice 2

What is "stressed"[::-1]?

HintA step of −1 walks the sequence backward.

'desserts'. [::-1] is the standard Python way to reverse any sequence, and s == s[::-1] is the one-line palindrome check.

Dictionaries and sets

A dictionary maps keys to values. Instead of asking for item number 3, you ask for the item named "alice":

ages = {"alice": 31, "bob": 27}
ages["alice"]            # 31
ages["carol"] = 45       # add or replace
"bob" in ages            # True  (checks keys)
ages.get("dave", 0)      # 0     (a default instead of a KeyError)
for name, age in ages.items(): ...

Dictionaries are fast. Looking up a key takes about the same time whether the dictionary has ten entries or ten million, because Python stores entries in a hash table: it turns each key into a number and uses that number to jump straight to the right slot. (Stage 3 shows how.) That trick only works if a key can't change after it's stored, so keys must be immutable: strings, numbers, and tuples work, lists don't. Since Python 3.7, dictionaries also keep keys in the order you inserted them.

A set is a dictionary with only keys: an unordered collection with no duplicates and the same fast in check. set(words) is the quickest way to remove duplicates.

The most common dictionary pattern is counting:

counts = {}
for word in "the cat and the hat".split():
    counts[word] = counts.get(word, 0) + 1
Practice 3

After the counting loop above, what is counts["the"]?

HintThe first time a word appears, get returns the default, 0.

2. The full result is {'the': 2, 'cat': 1, 'and': 1, 'hat': 1}. This pattern is common enough that the standard library has a ready-made version: collections.Counter("the cat and the hat".split()).

Practice 4

What is len(set("mississippi"))?

HintA string is a sequence of characters, and a set keeps one of each.

4: m, i, s, and p. Eleven characters, four distinct.

Check

You want a dictionary from map coordinates to the name of what's there. Which works as a key?

The tuple (3, 4). It's immutable, so its hash can never change after it's stored. grid[(3, 4)] = "tree", or just grid[3, 4], since the parentheses are optional there.

Building a data type

Python doesn't have a fraction type built in (well, it has one in the standard library, but pretend it doesn't). How would you make one? CS61A's answer starts with a decision to separate two kinds of code:

  • Code that uses fractions should think in terms of numerators and denominators.
  • Code that implements fractions decides how they're stored.

The two sides talk through a small set of functions. A constructor builds a value, and selectors take it apart:

def rational(n, d):      # constructor
    return (n, d)

def numer(x):            # selectors
    return x[0]

def denom(x):
    return x[1]

Everything else is written using only those three:

def add_rational(x, y):
    nx, dx, ny, dy = numer(x), denom(x), numer(y), denom(y)
    return rational(nx * dy + ny * dx, dx * dy)

def mul_rational(x, y):
    return rational(numer(x) * numer(y), denom(x) * denom(y))

Now look at the top panel again. The middle layer, add_rational and friends, never mentions tuples. That's why you can switch the bottom layer to a dictionary, or even to a function, and the answer stays the same.

Practice 5

Suppose rational reduces fractions to lowest terms. What is numer(mul_rational(rational(2, 3), rational(3, 4)))?

Hint2/3 × 3/4 = 6/12 before reducing. Try it on the panel with "Reduce to lowest terms" ticked.

6/12 reduces to 1/2, so the numerator is 1. Only the constructor had to change to add reducing; mul_rational didn't. One change in one place, which is the payoff of the barrier.

Abstraction barriers

The rule is simple to say: only cross a barrier through the official functions. A function like this one breaks it:

def print_rational(x):
    print(x[0], "/", x[1])     # reaches past numer and denom into the tuple

It works today, because fractions happen to be tuples. Switch the top panel to "Breaks the barrier", then change the storage to a dict. The code that cheated crashes, while everything that went through numer and denom keeps working. In a real codebase, that crash shows up months later, in code nobody remembers writing, when someone improves the representation.

Check

Which line inside add_rational respects the abstraction barrier?

The second one reads values only with selectors and builds the result only with the constructor. Option 3 is the subtle trap: it reads correctly but builds a tuple by hand, so it silently bypasses whatever the constructor does, like reducing.

Check

Fractions are switched from tuples to dicts like {"n": 1, "d": 2}. What does the barrier-breaking print_rational do now?

x[0] on a dict looks up the key 0, which doesn't exist: KeyError: 0. With the function representation it would be TypeError: 'function' object is not subscriptable. Either way, the bug is in print_rational, not in the change that exposed it.

Abstraction barriers are how large programs stay changeable. Python itself is an example: in Python 3.6, CPython switched to a completely new dictionary layout that used 20 to 25% less memory, and no one's code had to change, because nobody's code could see the old layout. In practice, Python marks "don't touch" parts with a leading underscore (_numer) and offers tools like dataclasses and classes (next lesson) to bundle data with its official functions.

Check

What's the main benefit of keeping all code behind the fraction functions?

Freedom to change the representation. Every program changes over its life. Barriers decide how much of it has to change along with each decision.

When this goes wrong

The year 2000 problem

In the 1960s and 70s, memory was expensive, so programs stored years as two digits: 75 for 1975. That was a reasonable representation. The problem was that it leaked everywhere. Instead of asking a date for its year through one shared function, millions of programs read the two digits directly, did arithmetic on them, sorted by them, and printed them. As 2000 approached, "00" would sort before "99" and ages would come out negative, and there was no single place to fix it: every program that touched a date had to be found, read, and changed by hand. Governments and companies spent hundreds of billions of dollars on the fix, and it mostly worked, which is why little went wrong on January 1, 2000. The lesson engineers took: hide representations behind functions, even when the representation looks too simple to change.

What to remember

  • Sequences share indexing, slicing ([start:stop:step], stop excluded), len, in, and iteration.
  • Lists change; tuples and strings don't. Only immutable values can be dictionary keys.
  • Dictionaries map keys to values with fast lookup. Sets are fast collections of unique items.
  • A data type is a constructor plus selectors. Code that uses the type should go through them.
  • An abstraction barrier lets the representation change without touching the code above it.

Try it in Python

The standard library's version of this lesson's fractions:

from fractions import Fraction

x = Fraction(1, 2) + Fraction(1, 3)
print(x)                    # 5/6
print(x.numerator)          # 5   (a selector)
print(Fraction(6, 12))      # 1/2 (the constructor reduces)
print(Fraction(1, 10) * 3 == Fraction(3, 10))   # True, unlike 0.1 * 3 == 0.3
