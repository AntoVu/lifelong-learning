Threads and race conditions

Processes are isolated from each other. Threads are the opposite: several flows of control inside one process, sharing all of its memory. That makes them fast and powerful, and it creates a new kind of bug, one that depends on timing, appears one run in a thousand, and vanishes when you look for it.

Two threads, one counter

Both threads run counter = counter + 1, which the CPU does in three steps. You are the scheduler: choose which thread runs each step. Can you make the counter end at 1 instead of 2?
shared memorycounter = 0

Now let each thread add 1 three times (expected total: 6), and try 1,000 random schedules.

Run T1's load, then T2's load, then both stores: each thread read 0, each wrote 1, and one increment vanished. That's a lost update. In the experiment, where a switch can happen after any step, most runs go wrong. Real threads usually run many instructions between switches, so the bad interleavings are rare, and rare is exactly what makes this bug dangerous: it passes testing and fails in production.

Threads

A thread is an independent sequence of execution within a process. Each thread has its own registers, program counter, and stack (its own chain of function calls), but all the threads of a process share the same address space: globals, the heap, open files. Creating and switching between threads is cheaper than processes, since there's no new address space or page table to set up.

Threads are used for two reasons. Parallelism: split work across several cores to finish sooner. Overlapping waits: while one thread waits for the disk or network, others keep working, which is how a web server handles thousands of requests at once.

Check

Which does each thread in a process get its own copy of?

Stack and registers, so each thread has its own local variables and its own place in the code. Everything else is shared, which is the source of both the power and the danger.

Race conditions

One line of code is usually several machine instructions. counter = counter + 1 is a load from memory into a register, an add, and a store back. A context switch can happen between any two instructions, and on a multicore machine the two threads may run at literally the same time. When the result depends on how the steps of different threads happen to interleave, that's a race condition.

This isn't hypothetical. A test for this lesson ran the C version, two threads each adding 1 a million times to a shared counter, on an ordinary laptop:

counter = 1632943 (expected 2000000)
counter = 1661993 (expected 2000000)
counter = 1032865 (expected 2000000)

Hundreds of thousands of updates lost, a different number every run. Adding a lock around the increment (next lesson) gave exactly 2,000,000 every time.

Practice 2

With each thread adding 1 three times (as in the panel's experiment), what's the smallest final value a schedule can produce?

HintNot 1. Think about a thread loading a value, sleeping through the other thread's work, and storing its stale result near the end.

2. T1 loads 0 and pauses. T2 does two full increments (counter 2). T1 stores 1, wiping them out. T2 loads that 1 and pauses. T1 finishes its other two increments (counter 3). T2 stores 2. Surprising, but it's a real schedule, and it's why reasoning "it can only be off by a little" fails.

Critical sections and atomic operations

A critical section is a piece of code that touches shared data and must not be interleaved with another thread's critical section on the same data. What we need is mutual exclusion: while one thread is inside, others wait. Locks, the next lesson, provide it.

Hardware helps by offering atomic instructions, which happen all at once with no possible interleaving: an atomic increment, or compare-and-swap ("if this memory still holds 5, set it to 6; tell me whether it worked"). Every lock is built on instructions like these.

Which of these is not a race condition risk?

Local variables live on each thread's own stack, so there's nothing shared to race on. The seat booking is a famous pattern called check-then-act, and it's a race even though each step looks safe.

Why these bugs are so hard

Race conditions depend on timing, which changes with machine load, CPU count, compiler settings, and even whether a debugger is attached. Adding a print statement can change the timing enough to make the bug disappear, which earned these bugs the nickname "Heisenbugs". A test suite that passes a thousand times proves little: the bad interleaving might need one specific microsecond to line up.

So the defenses are mostly about design: share as little as possible, protect what's shared with locks, prefer passing messages through thread-safe queues, and use tools like ThreadSanitizer (-fsanitize=thread), which watch every memory access during testing and report unsynchronized ones even when the bad timing didn't happen.

Check

A multithreaded test passes 999 times and fails once. You add logging, and it never fails again. What's most likely?

A hidden race. Printing takes a lock inside the I/O library and slows each thread, which shifts the interleavings. The bug is still there, waiting for production load.

Threads in Python

The standard CPython interpreter has a global interpreter lock (GIL): only one thread runs Python bytecode at a time. That protects the interpreter's own data structures, and it means threads don't speed up pure-Python computation. They still help with waiting on I/O, since a thread releases the GIL while it waits. In a test for this lesson, Python 3.14's version of the two-thread counter happened to give the right answer, because switches between threads rarely landed in the middle of the increment. That's luck, not safety: counter += 1 is still several bytecode instructions.

Python is changing here. PEP 703 added an optional build without the GIL ("free-threaded" Python), officially supported since Python 3.14, where threads really do run Python code in parallel, and races like the panel's show up the same way they do in C. For parallel computation today, the usual choices are the multiprocessing module (separate processes, each with its own interpreter) or libraries like NumPy that release the GIL inside compiled code. For handling many network connections, asyncio runs many tasks on one thread, switching only at await.

Check

You want to speed up a CPU-heavy pure-Python calculation on an 8-core machine, using standard CPython with the GIL. What helps?

Processes. Each has its own interpreter and GIL, so all 8 cores work at once. The cost is that processes don't share memory, so data must be sent between them.

When this goes wrong

Therac-25, 1985 to 1987

The Therac-25 was a radiation therapy machine controlled entirely by software, with the hardware safety interlocks of earlier models removed. Between 1985 and 1987 it gave six patients massive overdoses, by some estimates up to about 250 times the intended dose, and three of them later died. One of the causes was a race condition. If an experienced operator selected X-ray mode by mistake and then quickly edited it to electron mode, all within about eight seconds, one task was still setting up the machine with the old values while another accepted the edit. The beam fired at full X-ray power without the metal target that should have spread it. Slower operators never triggered it, so testing never found it. The investigation that followed became a founding case study in software safety, and a reason safety-critical systems keep hardware interlocks no matter how good the software seems.

What to remember

  • Threads share a process's memory; each has its own stack and registers.
  • One line of code is several instructions. Interleaving them across threads causes race conditions and lost updates.
  • Shared data needs critical sections with mutual exclusion; hardware atomic instructions make that possible.
  • Races are timing-dependent, rare, and easily hidden by debugging. Design to share less, and use sanitizers.
  • CPython's GIL limits parallel Python computation; use processes, compiled libraries, or the free-threaded build.

Try it in Python

Share work safely with a queue instead of a shared variable:

import threading, queue

results = queue.Queue()            # thread-safe: it has its own lock inside

def worker(n):
    results.put(n * n)

threads = [threading.Thread(target=worker, args=(i,)) for i in range(5)]
for t in threads: t.start()
for t in threads: t.join()

print(sorted(results.get() for _ in range(5)))   # [0, 1, 4, 9, 16]
