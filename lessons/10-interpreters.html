Interpreters: programs that run programs

Every lesson so far has used Python. But what is Python? Under the hood it's a program that reads your text and carries it out. In this lesson you'll build a tiny one yourself, in about 40 lines, and see that a programming language is just another abstraction.

A calculator language, step by step

Type an expression, or pick one. Watch it get split into tokens, parsed into a tree, and evaluated from the leaves up.

1. Tokenize: split the text into pieces

2. Parse: build a tree from the tokens

3. Evaluate: work out each part, from the leaves up

The language is a simplified version of Scheme, the language Berkeley's CS61A and MIT's classic SICP course use for exactly this purpose. Every operation goes first, inside parentheses: (+ 1 2) means 1 + 2, and (* 2 3 4) means 2 × 3 × 4. It looks odd, but it makes the structure of every expression explicit, which keeps the interpreter small.

A language is a program

When you type python script.py, you're running a program called the interpreter. The standard one, CPython, is written in C. It reads your file as plain text, works out its structure, compiles it to the bytecode you saw in stage 1, and then runs that bytecode in a loop. Your program is its data.

That's the stored-program idea from stage 1 one level up: there, instructions were bytes in memory; here, a whole language is text handled by a program. Once you see that, languages stop being magic. Each one is a set of decisions, written down as an interpreter or compiler, that anyone can read and change.

Reading: tokens and trees

An interpreter can't work with raw characters. The first stage, tokenizing (or lexing), splits the text into meaningful pieces: numbers, names, operators, and parentheses. For this language it's one line of Python, because spaces and parentheses are the only separators:

def tokenize(text):
    return text.replace("(", " ( ").replace(")", " ) ").split()

tokenize("(* (+ 1 2) 4)")
# ['(', '*', '(', '+', '1', '2', ')', '4', ')']
Practice 1

How many tokens does (* (+ 1 2) 4) have?

HintEvery parenthesis is its own token. Or type it into the calculator above and count.

9: four parentheses, two operators, and three numbers. Spaces aren't tokens; they just separate them.

Tokens are still a flat list. The second stage, parsing, builds the nested structure they describe: an expression tree (or abstract syntax tree). Each pair of parentheses becomes a node whose children are its parts. The parser is recursive, because the structure is: an expression can contain expressions.

def parse(tokens):
    token = tokens.pop(0)
    if token == "(":
        expr = []
        while tokens[0] != ")":
            expr.append(parse(tokens))    # each part is itself an expression
        tokens.pop(0)                     # drop the ")"
        return expr
    try:
        return int(token)
    except ValueError:
        return token                      # an operator, like "+"

parse(tokenize("(+ 1 (* 2 3))"))          # ['+', 1, ['*', 2, 3]]

Python itself does the same thing for its much bigger grammar, and lets you look at the result with the ast module. Notice how the tree, not the text, records that * happens before +:

>>> import ast
>>> print(ast.dump(ast.parse("1 + 2 * 3", mode="eval"), indent=2))
Expression(
  body=BinOp(
    left=Constant(value=1),
    op=Add(),
    right=BinOp(
      left=Constant(value=2),
      op=Mult(),
      right=Constant(value=3))))
Check

In Python's tree for 1 + 2 * 3, why is the Add node at the top?

The node at the top is the one computed last. Since * binds tighter, the parser makes 2 * 3 a subtree, and + combines 1 with its result. Precedence rules exist only in the parser; once the tree is built, there's no ambiguity left. Scheme skips precedence entirely by making you write the parentheses.

Evaluating: eval and apply

With a tree in hand, evaluating is short, because the tree's shape tells you exactly what to do. There are two cases:

  • A number evaluates to itself.
  • A call, like (* 2 3): evaluate each operand (recursively, since operands can be calls too), then apply the operator to the results.
import math, operator
from functools import reduce

def calc_eval(expr):
    if isinstance(expr, int):                # a number means itself
        return expr
    op, *operands = expr                     # a call: (op operand ...)
    args = [calc_eval(e) for e in operands]  # evaluate the parts first
    return calc_apply(op, args)

def calc_apply(op, args):
    if op == "+":
        return sum(args)
    if op == "*":
        return math.prod(args)
    if op == "-":
        return -args[0] if len(args) == 1 else args[0] - sum(args[1:])
    if op == "/":
        return reduce(operator.truediv, args)
    raise TypeError(f"unknown operator: {op}")

That's the whole interpreter: tokenize, parse, and these two functions. Step through the evaluation in the calculator above: values appear at the leaves first, then flow up to the root, exactly like the call tree in the recursion lesson. The pair of functions has a famous name. SICP calls it the eval-apply cycle: eval breaks expressions into parts, apply carries out operations, and they call each other until the answer is reached.

Practice 2

What does (- 10 2 3) evaluate to?

HintWith more than one argument, - subtracts all the rest from the first.

10 − 2 − 3 = 5. Letting operators take any number of arguments is one of Scheme's design decisions, and it lives entirely in calc_apply.

Practice 3

What does (+ 1 (* 2 (- 5 3))) evaluate to?

HintStart at the innermost parentheses and work outward.

(− 5 3) = 2, then (* 2 2) = 4, then (+ 1 4) = 5. Inside out, which is leaves up in the tree.

Practice 4

What does (*), a multiplication with no arguments, evaluate to?

HintLook at what math.prod must return for an empty list so that multiplying by it changes nothing.

1, the empty product, just as (+) is 0, the empty sum. These are the values that leave any number unchanged, and they're what math.prod([]) and sum([]) return.

The read-eval-print loop

Wrap the pieces in a loop and you have an interactive language:

while True:
    text = input("calc> ")
    print(calc_eval(parse(tokenize(text))))

Read, eval, print, loop: a REPL. Python's >>> prompt is exactly this, with a much bigger eval. So is your browser's JavaScript console, and so are the shells you'll meet in stage 8.

To grow the calculator into a real language, you'd add two things you already understand from the inside. Names: (define x 5) needs somewhere to store x, which is a frame, like the ones on the tracer. Functions: (lambda (n) (* n n)) needs a value that remembers its parameters, its body, and the frame it was defined in, which is a closure from lesson 1. CS61A's final project does exactly that, ending with an interpreter for most of Scheme.

Check

You add (define x 5) to the calculator. Which part of the interpreter has to change to make (+ x 1) work?

The evaluator. calc_eval gets a third case, "a name evaluates to its value in the environment", plus a special case for define, which must not evaluate x before storing it. Syntax and meaning are separate layers, another abstraction barrier.

Where interpreters hide

Once you know the shape, you'll find interpreters everywhere: SQL databases parse and evaluate queries (stage 7), spreadsheets parse formulas, regex engines interpret patterns (the Cloudflare story in lesson 2), and template engines, config languages, and build tools all read text and act on it. Writing a small one is often the cleanest solution to a problem.

The flip side: an interpreter does whatever its input says. Python's built-in eval(text) runs any Python expression, so passing it text from a user hands that user your whole program. eval("__import__('os').system('rm -rf ~')") is a valid expression. To read data like "[1, 2]" safely, use ast.literal_eval, which only accepts literals, or a format like JSON.

Check

A web form lets users type a math expression, and the server computes it with eval(user_text). What's the problem?

Arbitrary code execution. Anything Python can do, the user can now do on your server. The safe design is a small interpreter like this lesson's, which only understands numbers and four operators, so there's nothing else to exploit.

When this goes wrong

Log4Shell, 2021

Log4j is a Java library that writes log messages, used in a huge share of the world's Java software. Few people knew it contained a small interpreter: when it logged a string, it looked for patterns like ${...} and evaluated them. One kind, ${jndi:ldap://...}, told it to fetch an object from a server on the internet and load it, which could run that server's code. Since programs routinely log text that users send them, an attacker only had to type that pattern into a chat message, a username, or a web request header. The bug, made public in December 2021, scored the maximum 10 out of 10 for severity, and in Minecraft: Java Edition, one of the affected programs, an attacker could trigger it just by typing into the game's chat. Teams around the world spent weeks finding every copy. The lesson: know when your data is being interpreted.

What to remember

  • An interpreter is a program whose input is another program. Python itself is one.
  • Interpreting has stages: tokenize (text to pieces), parse (pieces to a tree), evaluate (tree to a value).
  • Precedence and grouping are settled by the parser. The tree has no ambiguity.
  • Evaluation is recursive: evaluate the parts, then apply the operation. Eval and apply call each other.
  • Names need environments (frames); functions need closures. You already know both.
  • Never eval untrusted text. Interpret only what you mean to allow.
