Scheduling

Many processes are ready to run, and a core can run one at a time. Which goes next, and for how long? The answer decides whether your laptop feels snappy or sluggish, and there's no single best policy, only tradeoffs. This lesson lets you try the classic ones.

Measuring a schedule

Two numbers capture what users feel:

  • Turnaround time = finish time − arrival time. How long until the job is done. It matters for batch work, like compiling or rendering a video.
  • Response time = first time it runs − arrival time. How long until something happens. It matters for anything interactive: you want your keystroke handled now, not after the video renders.

The table in the panel computes both for each job and averages them.

First in, first out

The simplest policy runs jobs in arrival order, each to completion. FIFO (first come, first served) is easy and fair in a sense, but it suffers from the convoy effect: short jobs stuck behind a long one wait for all of it, like shoppers with one item behind a full cart.

Practice 1

Jobs A (10 units), B (2), and C (2) all arrive at time 0 and run FIFO in the order A, B, C. What's the average turnaround time?

HintA finishes at 10, B at 12, C at 14. All arrived at 0.

(10 + 12 + 14) / 3 = 12. Check it in the panel with the convoy workload and FIFO.

Shortest job first

If the goal is low average turnaround, run the shortest job first (SJF). It's provably optimal for that goal when all jobs arrive together. But a long job that's already running still blocks short ones that arrive later. The fix is to allow preemption: whenever a job arrives, switch to whichever job has the least time left. That's shortest time-to-completion first (STCF). Try the staggered workload to see the difference.

Both share a big practical problem: the OS doesn't know how long a job will take. It's a useful ideal, and real schedulers approximate it by guessing from past behavior.

Practice 2

Same three jobs (A 10, B 2, C 2, all at time 0), now run shortest job first. What's the average turnaround? (Two decimal places.)

HintOrder B, C, A: they finish at 2, 4, and 14.

(2 + 4 + 14) / 3 = 20 / 3 ≈ 6.67, almost half of FIFO's 12, with exactly the same work done.

Check

Why don't real operating systems simply use shortest job first?

Job lengths are unknown. A program doesn't announce how long it will compute or when the user will click. Real schedulers watch how each process behaves and adjust.

Round robin

To respond quickly to everyone, round robin gives each ready job a short time slice (a quantum), then moves it to the back of the queue. Every job starts almost at once, so response time is excellent. Turnaround suffers, because every job is stretched out by sharing.

Choosing the slice is a tradeoff. Each switch costs a context switch, plus cold caches for the job that just started (stage 4). Slices too short waste time switching; slices too long feel like FIFO. Typical values are a few milliseconds.

Practice 3

Round robin with a quantum of 1, on A (10), B (2), and C (2), all arriving at 0 and queued in that order. What's the average response time?

HintA first runs at 0, B at 1, C at 2.

(0 + 1 + 2) / 3 = 1, versus about 7.3 for FIFO. But average turnaround rises to about 8.3, because A's work is spread over 14 time units.

Real schedulers

Real systems want both: snappy interactive programs and good throughput for long jobs, without knowing which is which. The classic answer is the multi-level feedback queue (MLFQ), first described by Fernando Corbató in 1962 for an early time-sharing system. It keeps several queues at different priorities and learns from behavior:

  • New jobs start at the top priority.
  • A job that uses its whole time slice is probably a long computation, so it moves down a level.
  • A job that gives up the CPU early, like an editor waiting for keystrokes, stays high. Interactive work keeps getting fast response.
  • Every so often, everything is boosted back to the top, so long jobs aren't starved forever.

Windows and macOS use priority schedulers in this family. Linux took a different route: since 2007 its schedulers (CFS, then EEVDF in 2023) aim for fairness, tracking how much CPU time each task has had and running the one that's had the least. That's the red-black tree from stage 3. With multiple cores, schedulers also try to keep each process on the same core, so its data stays in that core's cache.

Check

Under MLFQ, a text editor spends most of its time waiting for keystrokes and runs briefly after each one. Where does it end up?

High priority. Short bursts look interactive, so MLFQ keeps the editor responsive without ever being told it's an editor.

Check

In the Pathfinder story below, what fixed the repeated resets?

Priority inheritance. While the low-priority task held the lock the high-priority task needed, it borrowed the high priority, so medium-priority work couldn't push it aside.

When this goes wrong

Mars Pathfinder, 1997

Days after landing on Mars on July 4, 1997, the Pathfinder lander started resetting itself, losing data each time. Engineers at JPL reproduced it on an identical copy on Earth. A low-priority task that gathered weather data held a lock on a shared data bus. A high-priority task needed that lock and had to wait, which is normal. But medium-priority tasks, which didn't need the lock, kept preempting the low-priority one, so it never got to finish and release the lock. The high-priority task waited too long, a watchdog timer decided the system had hung, and it reset the computer. This is priority inversion. The operating system, VxWorks, already supported priority inheritance; it was just turned off. JPL uploaded a change to turn it on, and the resets stopped.

What to remember

  • Turnaround = finish − arrival; response = first run − arrival. Policies trade one against the other.
  • FIFO is simple but suffers the convoy effect. SJF and STCF minimize turnaround, but need job lengths no one knows.
  • Round robin gives great response at the cost of turnaround and context switches.
  • MLFQ learns from behavior: short bursts stay high priority. Linux instead runs whatever has had the least CPU.
  • Locks and priorities interact: priority inheritance prevents priority inversion.

Try it in Python

A tiny round-robin simulator:

from collections import deque

def round_robin(jobs, quantum=1):          # jobs: {name: length}, all arrive at 0
    queue, t, finish = deque(jobs.items()), 0, {}
    while queue:
        name, left = queue.popleft()
        run = min(quantum, left)
        t += run
        if left - run:
            queue.append((name, left - run))
        else:
            finish[name] = t
    return finish

print(round_robin({"A": 10, "B": 2, "C": 2}))   # {'B': 5, 'C': 6, 'A': 14}
