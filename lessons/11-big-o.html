Measuring cost: Big-O

Stage 2 was about writing programs that are clear. Stage 3 asks a second question: how fast are they, and how does that change as the input grows? This lesson gives you the vocabulary every later lesson, and every technical interview, uses to answer it.

The growth race

Slide n, the size of the input. Each bar is how many steps an algorithm of that kind takes, on a log scale, and the time at a billion steps per second.

Bar length is the number of digits in the step count, so each notch is 10 times more work. Red means more than a minute.

At n = 10, every algorithm is instant. At n = 1,000,000, one finishes in a nanosecond and another would outlast the universe. That difference comes from the shape of each algorithm, not from the speed of the computer, and Big-O is the way to describe that shape.

  • Work out the Big-O of loops, nested loops, and halving loops.
  • Spot accidentally quadratic Python code and fix it.

Count steps, not seconds

You could measure an algorithm with a stopwatch, but the result depends on the machine, the language, what else is running, and the particular input. What doesn't change is how the amount of work grows with the size of the input, which we call n: the length of a list, the number of users, the number of pixels.

So we count basic steps (an addition, a comparison, reading one item) as a function of n. Finding the largest of n numbers looks at each one once: about n steps. Comparing every pair of n numbers takes about n²/2 steps. Double n, and the first takes twice as long while the second takes four times as long. That ratio is what matters when your data grows from a test file to production.

Big-O notation

Exact counts get messy, like 3n² + 5n + 2. Big-O keeps only what dominates for large n, using two rules:

  • Drop lower-order terms. When n is a million, 3n² is 3 trillion and 5n is only 5 million. The n² term wins.
  • Drop constant factors. 3n² and n² grow the same way; the 3 depends on the machine and the details anyway.

So 3n² + 5n + 2 is O(n²), read "order n squared". Formally, f(n) is O(g(n)) if there are constants c and n₀ such that f(n) ≤ c · g(n) for every n ≥ n₀. In words: past some point, f never grows faster than g times a constant. Big-O is an upper bound. When people say "this is O(n)", they usually also mean "and not better", which is strictly Θ(n) (theta), the tight bound. Algorithms courses distinguish the two; everyday conversation rarely does.

Practice 1

An algorithm takes 4n² + 100n + 7 steps. What is its Big-O? (Type something like n^2.)

HintKeep the fastest-growing term and drop its constant.

O(n²). For small n, the 100n term is actually bigger (at n = 10: 400 vs 1,000). But past n = 25 the n² term takes over for good, and Big-O only cares about large n.

Check

Algorithm A takes 100n steps. Algorithm B takes n² steps. Which is faster for large inputs?

A, for n > 100. At n = 1,000, A takes 100,000 steps and B takes 1,000,000. At n = 1,000,000, A is 10,000 times faster. Constants decide small cases; growth decides big ones. (That's also why real libraries sometimes switch to a "worse" algorithm for tiny inputs.)

A useful rule of thumb: a modern computer does on the order of a billion simple steps per second. So at n = 1,000,000, O(n log n) takes milliseconds, O(n²) takes about 17 minutes, and O(2ⁿ) never finishes. Try it on the race above.

Practice 2

An O(n²) program takes 1 second on 1,000 items. Roughly how many seconds will it take on 10,000 items?

Hintn grew by 10 times. What happens to n²?

10 times the input means 10² = 100 times the work: about 100 seconds. This is how you predict whether something will survive real data: time it on a small input, then scale by the growth rate.

Reading the cost of code

You can usually read Big-O straight off the code's structure:

  • Steps in sequence add. A loop over n items, then another loop over n items, is n + n = O(n).
  • Nested loops multiply. A loop over n items inside a loop over n items is n · n = O(n²).
  • Function calls cost what the function costs. A loop that calls an O(n) function n times is O(n²), even though you only see one loop.
def has_duplicate(xs):
    for i in range(len(xs)):
        for j in range(i):           # every earlier item
            if xs[i] == xs[j]:
                return True
    return False
Practice 3

For a list of 10 items with no duplicates, how many times does has_duplicate run the comparison xs[i] == xs[j]?

HintThe inner loop runs 0 times, then 1, then 2, ..., up to 9.

0 + 1 + ... + 9 = 45, which is n(n − 1)/2. That's about n²/2, so the function is O(n²), even though the inner loop is "only half" of a full one. Halving is a constant factor, and Big-O drops constants.

Check

What's the Big-O of this function, for a list of n names?

def report(names):
    for name in names:
        print(name)
    for name in names:
        print(name.upper())

n + n = 2n steps, which is O(n). Two passes over the data are still linear. Only nesting multiplies.

Halving: binary search

How do you find a name in a sorted phone book of a million names? Not by reading from page one. Open the middle, see whether the name comes before or after, and throw away the half it can't be in. Repeat. Each step halves what's left:

def binary_search(xs, target):        # xs must be sorted
    lo, hi = 0, len(xs) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if xs[mid] == target:
            return mid
        elif xs[mid] < target:
            lo = mid + 1               # target is in the right half
        else:
            hi = mid - 1               # target is in the left half
    return -1

The number of times you can halve n before reaching 1 is log₂ n, so binary search is O(log n). Logarithms grow absurdly slowly: log₂ of a thousand is about 10, and log₂ of a billion is about 30. Whenever an algorithm throws away a constant fraction of the problem at each step, expect a log n.

Practice 4

At most how many times does binary search look at an item (xs[mid]) in a sorted list of 1,000,000 items?

Hint2¹⁰ = 1,024, so 2²⁰ is about a million. How many halvings get you down to one item?

20. 2²⁰ = 1,048,576, which is just over a million, so 20 looks always suffice. A linear scan could need a million. That's the difference between O(log n) and O(n).

Check

What's the Big-O of this loop?

steps = 0
while n > 1:
    n = n // 2
    steps += 1

O(log n). Halving n until it reaches 1 takes about log₂ n rounds. In fact this loop computes ⌊log₂ n⌋.

What Python operations cost

Big-O hides inside innocent-looking lines. These are worth memorizing:

OperationCostWhy
xs[i], xs.append(x), xs.pop()O(1)A list is an array; the end is cheap to reach (lesson 2)
x in xs for a listO(n)It checks items one by one
xs.insert(0, x), xs.pop(0)O(n)Every other item has to shift over
x in s for a set, d[k] for a dictO(1) on averageHash tables (lesson 3)
sorted(xs)O(n log n)Timsort (lesson 4)

The classic trap is an O(n) operation inside a loop. This looks like one loop, but it's O(n²):

seen = []
for x in items:
    if x not in seen:       # O(n) scan of a list, every time
        seen.append(x)

Changing seen = [] to seen = set() (and append to add) makes it O(n). On 100,000 items, checking a list takes around ten thousand times longer than checking a set.

Check

You need to check, for each of n orders, whether its customer ID is in a list of n banned IDs. What's the best fix for speed?

Build a set once (O(n)), then each check is O(1) on average: O(n) total instead of O(n²). Sorting once and using binary search would also work, at O(n log n).

When this goes wrong

GTA Online's six-minute load screen, 2021

For years, players of GTA Online waited several minutes for the game to load. In 2021 a player who goes by t0st profiled it without the source code and found the CPU spending about four minutes on a 10-megabyte JSON file with some 63,000 entries. There were two accidentally quadratic steps. The parser called sscanf for each value, and sscanf measured the length of the entire remaining 10 MB string every time. Then, to avoid duplicates, each of the 63,000 items was checked against every item already stored, about two billion comparisons, where a hash table would have needed 63,000 lookups. A small patch cut t0st's load time from about six minutes to under two. Rockstar confirmed the bug, shipped a fix, and paid him a $10,000 bug bounty.

What to remember

  • Measure how work grows with input size n, not seconds on one machine.
  • Big-O keeps the fastest-growing term and drops constants: 3n² + 5n is O(n²).
  • Sequences add, nesting multiplies, halving gives log n.
  • At a billion steps per second, n = 10⁶ is instant for O(n log n), minutes for O(n²), and impossible for O(2ⁿ).
  • Watch for O(n) operations inside loops: in on a list, insert(0), pop(0). Reach for sets and dicts.

Try it in Python

See the difference yourself:

import timeit

items = list(range(100_000))
as_list, as_set = items, set(items)

print(timeit.timeit(lambda: 99_999 in as_list, number=100))   # scans the list
print(timeit.timeit(lambda: 99_999 in as_set, number=100))    # one hash lookup
