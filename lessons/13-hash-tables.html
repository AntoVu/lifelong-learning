Hash tables

Arrays find item number i instantly but can't find the item named "alice" without searching. Hash tables combine the two: turn the name into a number, and use the number as an array index. It's the idea behind every Python dict and set, and one of the most useful tricks in computing.

Inside a hash table

Add keys and look them up. Watch which bucket each key's hash sends it to. Then switch to the bad hash function.

Each row is one slot of an array, called a bucket. To store a key, compute its hash, take the remainder after dividing by the number of buckets, and put it there. To find it again, do the same arithmetic and look in that one bucket. No searching through everything.

From key to index

A hash function turns any key into a whole number, its hash. A good one has three properties:

  • Deterministic: the same key always gives the same hash, or you'd never find anything again.
  • Spreads keys evenly: similar keys, like "cat" and "car", should land far apart.
  • Fast: it runs on every insert and lookup.

The panel uses a classic string hash: start at 0, and for each character, multiply by 31 and add the character's code. Then the bucket is the hash modulo the number of buckets:

def bucket_for(key, num_buckets):
    h = 0
    for ch in key:
        h = (h * 31 + ord(ch)) % 1_000_003     # keep the number manageable
    return h % num_buckets

Python's built-in hash() uses a stronger algorithm called SipHash for strings, but the job is the same.

Practice 1

A key's hash is 1234, and the table has 8 buckets. Which bucket does it go in?

HintTake the remainder after dividing by 8: 1234 = 8 × 154 + ?

1234 % 8 = 2. Buckets are numbered from 0, so the remainder is always a valid index.

Collisions

There are far more possible keys than buckets, so sometimes two keys land in the same bucket: a collision. They're not rare, either. In a room of just 23 people, there's a better than even chance that two share a birthday, even though there are 365 days. Collisions start early for the same reason, so every hash table needs a plan for them:

  • Chaining: each bucket holds a small list of every key that landed there. That's what the panel shows. Java's HashMap works this way.
  • Open addressing: each bucket holds one key; on a collision, probe other buckets in a fixed order until an empty one turns up. Python's dict does this.

Either way, a lookup goes to the right bucket and then compares keys until it finds a match, so a collision costs a few extra comparisons, not a wrong answer.

Practice 2

What's the smallest number of people for which the chance that two share a birthday is over 50%? (Ignore leap years.)

HintIt's surprisingly small: fewer than 30.

23 gives about 50.7%. With n people there are n(n − 1)/2 pairs, and 23 people make 253 pairs, each of which could match. For a hash table with m buckets, expect the first collision after only about √m keys.

Load factor and resizing

How long are the chains? On average, the number of keys divided by the number of buckets. That ratio, n/m, is the load factor. If it stays below a fixed limit, the average chain has a constant length, so lookup, insert, and delete are all O(1) on average.

To keep it there, a hash table resizes: when the load factor passes the limit, it allocates a bigger array (usually twice the size) and re-inserts every key, since each key's bucket depends on the array size. That's O(n), but like the dynamic array in the last lesson it happens rarely enough to average out. CPython resizes a dict when it's two-thirds full. Add keys in the panel and watch it double from 8 to 16 buckets.

Practice 3

A table has 8 buckets and holds 6 keys. What is its load factor?

HintKeys divided by buckets.

6 / 8 = 0.75. That's past Python's two-thirds limit, so a Python dict this full would already have resized.

Practice 4

A key with hash 1242 sits in bucket 2 of an 8-bucket table. The table resizes to 16 buckets. Which bucket does the key move to?

HintRecompute: 1242 % 16.

1242 = 16 × 77 + 10, so bucket 10. This is why resizing has to re-insert every key: the bucket depends on the table size. (When the size doubles, each key either stays put or moves up by exactly the old size, 2 + 8 = 10.)

The worst case

"O(1) on average" assumes the hash spreads keys evenly. Tick "Bad hash" in the panel: it uses each key's length, so all the five-letter animals pile into one bucket. With a chain of length n, a lookup checks every key in it: O(n). A hash table with a bad hash function is just a slow list.

Check

What's the worst-case cost of looking up a key in a hash table with n keys?

O(n). Real hash tables rarely get there by accident, but an attacker who knows your hash function can do it on purpose, which is exactly what happened in 2011. (Java 8 later added a defense: long chains in a HashMap turn into balanced trees, capping lookups at O(log n).)

What can be a key

A key's hash has to stay the same for as long as it's in the table. If you could change a list after using it as a key, its hash would change, and the table would look in the wrong bucket forever. That's why Python only allows immutable values like strings, numbers, and tuples as dict keys and set items. Python calls them hashable.

Your own classes are hashable by identity by default. If you define __eq__ to compare by value (stage 2), you must also define __hash__, and keep the one rule that makes hash tables work: objects that are equal must have equal hashes. The reverse isn't required; unequal objects may share a hash, which is just a collision.

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)
    def __hash__(self):
        return hash((self.x, self.y))      # equal points give equal hashes
Check

A class's __eq__ says two objects are equal when their names match, but its __hash__ also mixes in a random number per object. What goes wrong?

Missed lookups. The table only compares keys inside one bucket. If equal objects hash differently, key in d looks in the wrong bucket and says False even though an equal key is stored.

Check

Since 2012, Python picks a random secret value at startup and mixes it into every string hash. Why?

If attackers can't predict the hash, they can't craft thousands of keys that collide. That's also why hash("cat") prints a different number each time you start Python, and why you must never save those numbers to a file or send them to another process.

When this goes wrong

Hash flooding, 2011

At the Chaos Communication Congress in December 2011, Alexander Klink and Julian Wälde showed that the web servers behind PHP, Java, Python, Ruby, and ASP.NET could be knocked over with a single request. Web frameworks put a form's fields into a hash table, and the hash functions were public and predictable. So the researchers computed many thousands of field names that all landed in the same bucket. Inserting them turned O(1) operations into an O(n²) pile-up, and a single crafted request could keep a server's CPU busy for minutes. Languages responded by randomizing their hash functions per process. Python made that the default in version 3.3, and in 3.4 switched strings to SipHash, a function designed to resist exactly this attack.

What to remember

  • A hash table turns a key into an array index: hash(key) % number_of_buckets.
  • Collisions are normal (the birthday problem). Chaining and open addressing both handle them.
  • Keeping the load factor bounded by resizing makes operations O(1) on average.
  • The worst case is O(n), when keys pile into one bucket. Randomized hashes keep attackers from forcing it.
  • Keys must be immutable. Equal objects must have equal hashes.

Try it in Python

print(hash("cat"))              # changes every time you restart Python
print(hash(42), hash((1, 2)))   # small ints hash to themselves; tuples combine their items

d = {}
try:

except TypeError as e:
