The memory hierarchy and caches

Stage 1 mentioned that main memory takes hundreds of clock ticks to answer. CPUs hide that with caches, and whether your code works with them or against them can change its speed by ten times or more, with the same Big-O and the same answer. This lesson shows how.

Sum a matrix two ways

An 8×8 matrix of ints, stored row by row. The cache holds 4 lines of 4 ints each. Run both loop orders and compare the hit rates.

Cache (4 lines, least recently used is replaced)

Row by row, each miss brings in a line of 4 ints, and the next 3 reads are free: 75% hits. Column by column, every read lands on a different line, and with only 4 lines in the cache, each one is thrown out before it's needed again: 0% hits. Real caches are much bigger, but real matrices are bigger still. Summing a 4096×4096 matrix in C, the column-order loop ran about 10 times slower than the row-order loop in a test for this lesson.

The memory hierarchy

Fast memory is expensive and has to sit close to the CPU, so there's only a little of it. Cheap memory is slow and far away. So computers use a hierarchy: a small, fast level in front of a bigger, slower one, several times over. These figures come from Peter Norvig's widely shared table of approximate timings:

OperationTimeIf an L1 read took 1 second
Read from L1 cache0.5 ns1 second
Read from L2 cache7 ns14 seconds
Read from main memory (RAM)100 ns3.3 minutes
Seek to a new spot on a spinning disk8 ms6 months
Send a packet from the U.S. to Europe and back150 ms9.5 years

Exact numbers vary by machine and have improved for some levels (SSDs answer in tens of microseconds, not milliseconds), but the shape of the table hasn't changed: every step down the hierarchy is roughly ten to a thousand times slower than the one above.

Practice 1

Using the table, how many times slower is a read from main memory than a read from L1?

Hint100 ns divided by 0.5 ns.

200 times. A CPU that has to wait for RAM on every read spends almost all its time waiting, which is why the cache's hit rate matters so much.

How a cache works

A cache keeps copies of recently used memory. When the CPU reads an address, the cache checks whether it has a copy: a hit answers in a nanosecond or so; a miss fetches from the next level down and keeps a copy for next time. When the cache is full, it evicts something, usually the line used least recently.

Caches never fetch a single byte. They move memory in fixed-size blocks called cache lines, 64 bytes on nearly every modern CPU. Reading one int brings in the 15 ints around it, on the bet that you'll want them soon. Modern CPUs have two or three levels: a small L1 (tens of KB) per core, a bigger L2, and an L3 of several MB shared by all the cores.

Practice 2

How many 4-byte ints fit in one 64-byte cache line?

HintDivide.

64 ÷ 4 = 16. The panel uses 4 ints per line to keep the picture small; real lines hold 16.

Practice 3

Reading a big int array from start to end with 64-byte lines, what percentage of reads are cache hits? (Assume one miss per line.)

HintOne miss brings in 16 ints. How many of those 16 reads hit?

15 of every 16: 93.75%. In practice it's even better, because CPUs notice the pattern and prefetch the next lines before you ask.

Locality

Caches work because real programs have locality:

  • Temporal locality: if you used something recently, you'll probably use it again soon. A loop counter, a running total, a function called in a loop.
  • Spatial locality: if you used something, you'll probably use what's next to it soon. Walking through an array, reading the fields of one struct.

Code with good locality runs at cache speed. Code without it runs at memory speed. That's the difference the panel shows, and the reason behind the linked list vs. array result from stage 3: following next pointers jumps around memory, so each node can be a fresh miss.

Check

In for (i = 0; i < n; i++) total += a[i];, which kind of locality does reading a[i] show?

Spatial. Consecutive elements share cache lines. The variable total, used every iteration, shows temporal locality.

Writing cache-friendly code

C stores a 2D array row by row (row-major order), so m[i][j] and m[i][j+1] are neighbors, while m[i][j] and m[i+1][j] are a whole row apart. That's why loop order matters:

// fast: inner loop walks along a row
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += m[i][j];
// slow: inner loop jumps between rows
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += m[i][j];

Other habits follow from the same idea: prefer arrays to linked structures in hot loops; keep data that's used together, stored together; and for big matrix work, process the data in small tiles that fit in the cache. Python's NumPy library stores arrays row-major too, and its fast operations are fast largely because they walk memory in order inside compiled code.

Check

A C program processes a large image[height][width] array. Which loop nesting is faster?

Rows outside, columns inside, so the inner loop walks consecutive addresses in each row. Compilers sometimes swap loops for you, but not reliably, so write it the right way.

Caches everywhere

The same trick, keeping a small fast copy in front of something big and slow, appears at every level of computing: the operating system keeps recently read disk blocks in RAM; your browser keeps images and scripts it already downloaded; content delivery networks keep copies of websites in data centers near you; and applications put Redis or Memcached in front of their databases. Stage 2's @cache was one too.

Every cache has the same hard problem: the copy can go stale when the original changes. Deciding when to throw a copy away is called cache invalidation, and it's hard enough to have inspired the programming joke, attributed to Phil Karlton: "There are only two hard things in computer science: cache invalidation and naming things."

Check

A website caches product prices for 10 minutes to take load off its database. What's the risk?

Stale data. Every cache trades freshness for speed. Real systems shorten the time limit for data that changes often, or actively remove (invalidate) the cached copy whenever the original changes.

Where this idea comes from

Numbers every programmer should know

The table at the top of this lesson comes from Peter Norvig's essay "Teach Yourself Programming in Ten Years", and Google's Jeff Dean spread a version of it through talks to engineers, where it became known as "latency numbers every programmer should know". Its point isn't the exact values, which change with every hardware generation. It's that the gaps are enormous and stable: registers and caches are a thousand times faster than a trip to RAM, which is a thousand times faster than a disk seek, which is many times faster than a trip across an ocean. Designs that respect those gaps, by keeping hot data close and doing expensive trips rarely and in bulk, beat cleverer designs that don't.

What to remember

  • Memory is a hierarchy: registers, L1, L2, L3, RAM, disk, network, each much bigger and much slower than the last.
  • Caches move 64-byte lines. Hits cost about a nanosecond; misses cost up to a hundred.
  • Temporal locality reuses data; spatial locality uses neighbors. Both make caches work.
  • In C and NumPy, arrays are row-major: loop over rows outside and columns inside.
  • Caching is everywhere, and every cache must decide when its copy is stale.

Try it yourself

Compile with gcc -O2 cache.c -o cache and run it to see the gap on your machine:

#include <stdio.h>
#include <time.h>
#define N 4096
static int m[N][N];

int main(void) {
    for (int i = 0; i < N; i++)          // fill it first: untouched memory can
        for (int j = 0; j < N; j++)      // all map to one shared zero page
            m[i][j] = i ^ j;
    long long s = 0;
    clock_t t = clock();
    for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) s += m[i][j];
    double rows = (double)(clock() - t) / CLOCKS_PER_SEC;
    t = clock();
    for (int j = 0; j < N; j++) for (int i = 0; i < N; i++) s += m[i][j];
    double cols = (double)(clock() - t) / CLOCKS_PER_SEC;
    printf("rows: %.3fs  columns: %.3fs  (%lld)\n", rows, cols, s);
}
