Locks, deadlock, and synchronization

The last lesson's races have a simple fix: a lock, so only one thread at a time can touch the shared data. But locks bring their own failure. Two threads can each hold a lock the other needs, and wait for each other forever. This lesson covers both, and the tools that help you avoid them.

Make two threads deadlock

Each thread needs both locks to do its work. Choose which thread takes each step. Can you get them stuck? Then switch on the fix and try again.

The deadlock takes just two steps: T1 locks A, then T2 locks B. Now T1 waits for B, which T2 holds, and T2 waits for A, which T1 holds. Neither can move, and nothing will ever free them. With the fix, both threads take the locks in the same order, A then B, and no schedule can get stuck.

Locks

A lock (also called a mutex, for mutual exclusion) has two operations. acquire takes the lock if it's free, or waits until it is. release gives it back. Put every access to the shared data between the two, and only one thread can be inside at a time:

import threading

counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(1_000_000):
        with lock:              # acquire; released automatically, even on an exception
            counter += 1

Locks are built from the atomic hardware instructions mentioned last lesson. When a lock is taken, a waiting thread can either spin (keep checking, good for very short waits) or ask the OS to put it to sleep until the lock is released (good for longer ones). Real locks usually spin briefly, then sleep.

2,000,000, every run. It was also noticeably slower than the broken version, which is the next section.

The cost of locking

A lock makes a critical section run one thread at a time, so it's a piece of your program that can't use more than one core. Amdahl's law from stage 4 applies directly: the more time spent holding locks, the less extra cores help. And when many threads want the same lock (contention), they spend their time waiting instead of working.

That creates a design choice. Coarse-grained locking, one lock for a whole data structure, is simple and hard to get wrong, but it serializes everything. Fine-grained locking, say one lock per bucket of a hash table, lets threads work on different parts at once, but there are more locks to get right, which leads straight to the next problem.

Check

A web server uses one global lock around its entire in-memory cache. Under heavy load, adding more CPU cores barely helps. Why?

Contention on one lock. The fix is finer-grained locking (for example, split the cache into shards, each with its own lock) or a data structure designed for concurrent access.

Deadlock

A deadlock is a set of threads each waiting for something another one holds, so none can proceed. In 1971, Edward Coffman and colleagues showed that a deadlock requires four conditions at once:

  1. Mutual exclusion: a resource can be held by only one thread.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: resources can't be taken away from a thread.
  4. Circular wait: there's a cycle of threads, each waiting for the next.

Break any one and deadlock is impossible. The most practical target is circular wait: give the locks a fixed global order, and always acquire them in that order. A cycle would need some thread to take a "later" lock before an "earlier" one, which the rule forbids. That's the panel's fix. (Other approaches exist, like taking all locks at once or giving up and retrying after a timeout, but lock ordering is the everyday one.)

Check

Which deadlock condition does "always lock A before B" break?

Circular wait. If everyone takes A before B, nobody can hold B while waiting for A, so the cycle can't form.

The classic illustration is Dijkstra's dining philosophers: five philosophers around a table, one fork between each pair, and each needs both neighboring forks to eat. If all five pick up their left fork at the same moment, everyone waits forever for a right fork.

Practice 2

In that deadlock, how many forks are being held?

HintEach philosopher holds their left fork.

All 5: every fork is held, and each philosopher waits for one held by a neighbor, a cycle of five. The lock-ordering fix: number the forks and always pick up the lower-numbered one first. One philosopher then reaches for their right fork first, and the cycle can't close.

Waiting for something to happen

Locks protect data, but threads also need to wait for events: a consumer waits until a queue has an item; a producer waits until there's room. Checking in a loop (busy-waiting) burns CPU. A condition variable lets a thread release its lock and sleep until another thread signals that something changed. A semaphore, invented by Dijkstra in the 1960s, is a counter with wait and signal operations, useful for limiting how many threads may use something at once, like ten database connections.

Check

What problem does a condition variable solve?

Efficient waiting. The waiting thread sleeps, using no CPU, until another thread signals. It must still recheck the condition when it wakes, because another thread may have gotten there first.

Higher-level tools

Low-level locks are easy to misuse, so most real code reaches for higher-level tools first:

  • Thread-safe queues (queue.Queue in Python): one set of threads puts work in, another takes it out, and the queue handles all the locking.
  • Message passing: threads don't share data at all; they send each other messages. Go's guideline sums it up: "Do not communicate by sharing memory; instead, share memory by communicating."
  • Immutable data: if nothing can change, there's nothing to race on.
  • Concurrent data structures built by experts, like Java's ConcurrentHashMap.

When this goes wrong

The Northeast blackout, 2003

On August 14, 2003, a power line in Ohio sagged into a tree and shut off. That kind of fault happens all the time, and the control room's alarm system is supposed to warn operators so they can reroute power. But a race condition in the alarm software, General Electric's XA/21 energy management system, had stalled it, silently. For over an hour, operators at FirstEnergy saw no alarms while more lines failed, and they didn't know their screens were frozen. The failures cascaded until at least 265 power plants shut down and about 55 million people in the U.S. and Canada lost power, some for days. A rare timing between parts of the software had left the alarm process stuck, the kind of bug the last two lessons describe.

What to remember

  • A lock gives mutual exclusion: acquire before touching shared data, release after. In Python, use with lock:.
  • Locked sections run one thread at a time, so contention limits scaling. Coarse locks are simple; fine locks scale but are harder.
  • Deadlock needs mutual exclusion, hold and wait, no preemption, and circular wait. Prevent it by always taking locks in one global order.
  • Condition variables and semaphores let threads wait for events without spinning.
  • Prefer queues, message passing, and immutable data over hand-rolled locking.

Try it in Python

A producer and consumer, with all the synchronization inside the queue:

import threading, queue

jobs = queue.Queue(maxsize=3)       # put() waits when full, get() waits when empty

def producer():
    for i in range(6):
        jobs.put(i)
    jobs.put(None)                  # a signal that there's no more work

def consumer():
    while (item := jobs.get()) is not None:
        print("processed", item)

threading.Thread(target=producer).start()
consumer()
