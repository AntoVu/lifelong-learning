Reading assembly

Stage 1 built a toy computer with nine instructions. A real x86-64 processor has over a thousand, but the code compilers actually produce uses a few dozen, and they work just like the toy ones. This lesson teaches you to read them, which is how you debug crashes, understand performance, and see what your compiler did with your code.

Why read assembly

You'll rarely write assembly. But you'll read it when a program crashes without source code (a debugger shows you the instruction that faulted), when you need to know why a loop is slow, when you're checking whether the compiler vectorized something, and in security work, where malware and exploits only exist as machine code. Compiler Explorer (godbolt.org) shows the assembly for any snippet in any major compiled language, and it's the easiest way to keep practicing.

Registers

x86-64 has 16 general-purpose 64-bit registers. Their names are historical: rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, and r8 through r15. Each also has smaller views: eax is the low 32 bits of rax, which is why 32-bit int code uses the e names. Two registers have fixed jobs: rsp is the stack pointer from the last lesson, and rip is the program counter from stage 1. The ALU flags from stage 1 (zero, sign, carry, overflow) live in a flags register that comparisons set and conditional jumps read.

Check

What is eax?

The low 32 bits of rax. (A quirk: writing to eax also clears the top 32 bits of rax.) Functions returning an int leave it in eax.

The instructions you'll see

This lesson uses Intel syntax, where the destination comes first: add eax, edx means eax = eax + edx. (Linux tools often default to AT&T syntax, which reverses the order and adds % signs; Compiler Explorer lets you pick.)

InstructionMeaning
mov a, ba = b. Square brackets mean memory: mov eax, [rdi] loads the int at the address in rdi (that's *p).
add a, b / sub a, ba = a + b / a = a − b, setting the flags
lea a, [x + y*4]"Load effective address": computes the address expression without touching memory. Compilers use it as a quick calculator.
cmp a, b / test a, bCompute a − b (or a AND b), keep only the flags
jmp L, je, jne, jl, jle, ...Jump, always or only if the flags say equal, not equal, less, ... (stage 1's JMP and JZ)
call f / retPush the return address and jump to f / pop it and jump back
push x / pop xPut x on the stack / take it off
Practice 1

With edi = 5 and esi = 7, what is in eax after lea eax, [rdi+rsi]?

Hintlea computes the expression in the brackets and stores it, without reading memory.

5 + 7 = 12. That one instruction is the whole add function at -O1. It adds two registers into a third, which plain add can't do.

Calling conventions

How does a function know where its arguments are? A calling convention, an agreement every compiler on the platform follows. On Linux and macOS (the System V convention), the first six integer or pointer arguments go in rdi, rsi, rdx, rcx, r8, and r9, and the return value comes back in rax. Windows uses a different list (rcx, rdx, r8, r9), which is one reason compiled programs aren't portable between the two.

The convention also says the stack pointer must be a multiple of 16 when a call happens. A call pushes an 8-byte return address, so on entry to g the stack is 8 bytes off. That's why g at -O1 subtracts 8 from rsp before calling f, and adds it back afterward.

Practice 2

On Linux, which register holds the second integer argument of a function? (Give the 64-bit or 32-bit name.)

HintThe order is rdi, rsi, rdx, rcx, r8, r9.

rsi (or esi for a 32-bit int). In max, a arrives in edi and b in esi.

Check

Why does g start with sub rsp, 8 even though it has no local variables?

Alignment. The incoming return address left the stack 8 bytes off a multiple of 16; subtracting 8 fixes it. Some instructions (used in f or library code) crash on misaligned data, so the convention guarantees it at every call.

Branches and loops

Assembly has no if or for, only compare and jump, exactly like the toy computer. An if becomes cmp followed by a conditional jump around the code that shouldn't run. A loop becomes a block of code ending in a conditional jump back to its start. Look at sum at -O1: the four lines from .L5 to jne .L5 are the entire loop.

Sometimes the compiler avoids jumping altogether. max uses cmovge, "conditional move if greater or equal", which picks one value or the other without a branch. That sidesteps the branch-prediction penalty from stage 1 when the outcome is unpredictable.

Practice 3

At -O1, how many instructions does sum's loop run per array element?

HintCount from the line after .L5: through jne .L5.

4: add the item, move the pointer 4 bytes, compare with the end, jump back. Notice there's no i at all. The compiler turned a[i] into a pointer that walks the array, the pointer arithmetic from lesson 1.

What the optimizer does

At -O0, GCC translates each line separately and keeps every variable in its stack slot, so a debugger can show and change any variable at any line. At -O1 and above, it keeps values in registers, deletes work whose result is never used, replaces index loops with pointer walks, inlines small functions, and at -O2 and -O3 may process several array items per instruction (vectorization). The rule it follows is the "as-if" rule: the optimized program must behave as if it ran your code as written, for every program that follows the language's rules.

That last part matters. If your code has undefined behavior, like reading past an array or overflowing a signed int, the compiler is allowed to assume it never happens. Optimized builds can then do things that look impossible from the source, such as deleting a safety check. That's why the same buggy program can work at -O0 and fail at -O2.

Check

Why is -O0 code full of loads and stores to addresses like [rbp-4]?

Debuggability. It's slow but predictable. Release builds use -O2 and ship separate debug information to map instructions back to source lines.

When this goes wrong

Reflections on Trusting Trust, 1984

Accepting the Turing Award, Ken Thompson, co-creator of Unix, described an attack that can only be seen in machine code. Modify a C compiler so that when it compiles the Unix login program, it inserts a secret password that always works. Then modify it so that when it compiles a compiler, it inserts both tricks into the new compiler. Compile it once, and remove the changes from the source code. Every future compiler built from the clean source will still carry the backdoor, and so will every login it builds, with nothing visible in any source file. Thompson's conclusion: "You can't trust code that you did not totally create yourself." Modern defenses include reproducible builds, where independent parties rebuild the same source and check that the machine code matches bit for bit.

What to remember

  • x86-64 has 16 general registers; eax is the low half of rax; rsp is the stack pointer, rip the program counter.
  • Intel syntax puts the destination first. Brackets mean memory. lea computes addresses (and quick math).
  • On Linux, arguments arrive in rdi, rsi, rdx, rcx, r8, r9; results return in rax.
  • Branches are cmp plus a conditional jump; loops jump backward; cmov avoids a branch.
  • Optimizers keep values in registers and restructure loops, under the as-if rule. Undefined behavior voids the deal.

Try it yourself

Paste any function into Compiler Explorer and compare -O0 with -O2. Or, with GCC installed:

gcc -O1 -S -masm=intel sum.c -o sum.s    # writes the assembly to sum.s
objdump -d -M intel ./program             # disassembles a compiled program (Linux)
