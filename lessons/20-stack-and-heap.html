The stack and the heap

Every variable needs memory, but not every variable needs it for the same amount of time. A loop counter lives for one function call; a list of users might live for the whole program. Running programs keep those two kinds in two different places, the stack and the heap. Knowing which is which explains a whole family of bugs.

Follow a program's memory

Step through. Function calls push frames onto the stack and pop them on return. malloc carves a block out of the heap that stays until free.

    A program's memory map

    When the operating system starts a program, it gives the new process its own range of addresses and divides it into regions:

    The stack

    You met the call stack in stage 1: one frame per active function call, holding its parameters, local variables, and the return address. In memory, it's one contiguous region, and a CPU register (the stack pointer) marks its top. Calling a function moves the pointer to make room for a frame; returning moves it back. That makes stack allocation almost free, a single subtraction, and cleanup automatic.

    The catch is in "automatic". When a function returns, its frame is gone, and the next call reuses that memory. So a pointer to a local variable is only valid while its function is running:

    int *broken(void) {
    int x = 42;
    return &x;          // x's frame is about to be reused: this address is garbage
}

    The stack is also small, typically 8 MB on Linux and 1 MB on Windows for the main thread. A huge local array, or recursion that goes too deep, runs off the end: a stack overflow.

    Check

    What's wrong with broken() above?

    It returns a dangling pointer into a dead frame. Compilers warn about this one ("function returns address of local variable"). The fix is to allocate on the heap, as make_array does, or to let the caller pass in the memory.

    The heap

    For memory that must outlive a function call, or whose size you only learn while running, C uses the heap. malloc(n) asks for n bytes and returns a pointer to them; the block stays yours until you call free on it:

    int *make_array(int n) {
    int *a = malloc(n * sizeof(int));   // n ints on the heap
    for (int i = 0; i < n; i++)
        a[i] = i * i;
    return a;                           // fine: the block outlives this frame
}
...
free(squares);                          // the caller gives it back when done

    Behind malloc is an allocator, library code that keeps track of which parts of the heap are in use and asks the operating system for more when needed. It's much slower than moving a stack pointer, and over time free blocks can end up scattered in small pieces (fragmentation). Despite the name, this "heap" has nothing to do with the heap data structure from stage 3.

    Practice 1

    How many bytes does malloc(n * sizeof(int)) request when n is 4?

    HintAn int is 4 bytes.

    4 × 4 = 16. malloc only counts bytes, so you have to multiply by the item size yourself. Forgetting sizeof is a classic way to allocate a quarter of what you need.

    Memory bugs

    Manual memory management gives C its speed and its most famous bugs:

    BugWhat happensTypical result
    LeakYou lose the last pointer to a block without freeing itMemory use creeps up until the program is killed
    Use after freeYou use a dangling pointer to a freed blockReads or corrupts whatever reuses that memory; often exploitable
    Double freeYou free the same block twiceCorrupts the allocator's bookkeeping
    Overflow / over-readYou write or read past the end of a blockCorrupts neighbors, or leaks secrets (see Heartbleed below)

    These aren't rare. Microsoft and the Chrome team have each reported that about 70% of their serious security bugs are memory safety problems like these. Tools catch many of them in testing: Valgrind and AddressSanitizer watch every memory access while your program runs and report the line that went wrong.

    Check

    A server calls malloc for every request but sometimes forgets to free. What happens over days of uptime?

    A leak. The memory is only returned when the process exits, which is why "restart it every night" is a real (if embarrassing) fix for leaky services.

    Letting the language manage it

    Most languages take free out of your hands:

    • Python puts every object on the heap and keeps a reference count in each one: how many names and containers point at it. When the count drops to zero, the memory is freed immediately. A separate cycle collector cleans up groups of objects that only point at each other.
    • Java, C#, Go, and JavaScript use a garbage collector that periodically finds every object still reachable from the program's variables and frees the rest. You never free anything, at the cost of some extra memory and occasional pauses.
    • Rust checks ownership rules at compile time, so every block has exactly one owner and is freed when the owner goes out of scope. No collector, and no use-after-free; the compiler rejects the program instead.

    That's why the dangling pointer from the panel can't happen in Python: as long as squares refers to the list, the list can't be freed.

    Check

    In Python, when is a list's memory freed?

    When the last reference goes away. sys.getrefcount(x) shows the count (one higher than you'd expect, because passing x to the function adds a temporary reference).

    Practice 3

    In the Heartbleed story below, the request's length field was 16 bits. What's the largest length an attacker could ask for?

    HintStage 1, lesson 1: the largest unsigned value in n bits is 2ⁿ − 1.

    2¹⁶ − 1 = 65,535 bytes, about 64 KB of server memory per request, and an attacker could send as many requests as they liked.

    When this goes wrong

    Heartbleed, 2014

    OpenSSL, the library that encrypted a large share of the web's traffic, supported a "heartbeat": the client sends a few bytes and a number saying how long they are, and the server echoes them back to show the connection is alive. The code trusted the number. Send 1 byte but claim 64 KB, and the server copied 64 KB starting at your byte, a buffer over-read, sending back whatever was next to it on the heap: session cookies, passwords, even the server's private keys. The bug sat in OpenSSL for two years before its disclosure on April 7, 2014, when about 17% of the internet's secure web servers, around half a million, were vulnerable. The fix was a single bounds check.

    What to remember

    • A process has code, globals, a heap that grows up, and a stack that grows down.
    • The stack holds frames: fast, automatic, small, and gone when the function returns.
    • The heap holds data that must outlive a call: malloc to get it, free to return it.
    • Leaks, use-after-free, double frees, and overflows cause most serious security bugs in C and C++.
    • Python counts references, Java and Go collect garbage, and Rust checks ownership at compile time.

    Try it yourself

    Watch Python's reference counts move:

    import sys

data = [1, 2, 3]
print(sys.getrefcount(data))   # 2: the name data, plus the temporary argument
alias = data
print(sys.getrefcount(data))   # 3: alias refers to the same list
del alias
print(sys.getrefcount(data))   # 2 again
