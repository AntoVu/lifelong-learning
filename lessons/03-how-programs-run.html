Programs are data

The first electronic computers were programmed by hand. To change what ENIAC computed in 1945, operators spent days moving cables and setting switches. The program was the wiring.

The fix was the stored-program idea, described in John von Neumann's 1945 report on the EDVAC, building on work by J. Presper Eckert and John Mauchly: keep the program in the same memory as the data, as numbers. Loading a new program is then just writing new bytes. The Manchester Baby ran the first stored program on June 21, 1948, and nearly every computer since has worked this way.

Look at the memory in the toy computer. There's nothing that marks a byte as "code" or "data". In the Add program, address E holds 1C, the number 28. Its cell also shows LDA 12, because that's what those bits would mean if the CPU ever fetched them. Whether a byte is an instruction depends only on whether the CPU tries to run it.

Check

How does the CPU know that the byte at address E of the Add program is data and not an instruction?

The CPU only runs what the program counter points to. The program halts at address 3, so it never fetches address E. If a bug sent the program counter there, the CPU would happily run 28 as LDA 12. That flexibility is powerful, and you'll see at the end of the lesson how attackers abuse it.

Instructions are numbers

The toy computer's instructions are one byte each. The top 4 bits are the opcode, which says what to do. The bottom 4 bits are the operand, usually a memory address. Four bits can name 16 addresses, which is exactly how much memory there is. It has one working register, A (the accumulator), and a zero flag, Z, from the ALU in lesson 2.

OpcodeInstructionWhat it does
0HLTStop the machine
1LDA aLoad: copy the byte at address a into A
2ADD aA = A + the byte at address a; set Z if the result is 0
3SUB aA = A − the byte at address a; set Z if the result is 0
4STA aStore: copy A into address a
5LDI nLoad immediate: A = n, the operand itself (0 to 15)
6JMP aJump: continue running from address a
7JZ aJump to a only if Z is set
8OUTShow A on the output

The control unit is the circuit that does this split. Its job is to look at the opcode and set the control lines from lesson 2: which register gets written, which operation the ALU runs, whether memory is read or written. Writing programs as hex bytes gets old fast, so people write them as assembly language, like ADD 15, and a program called an assembler turns each line into its byte.

Fetch, decode, execute

The CPU needs to remember where it is in the program. That's the job of one special register, the program counter (PC), which holds the address of the next instruction. A second register, the instruction register (IR), holds the instruction being worked on. Then the CPU repeats three steps for as long as it's powered on:

Go back to the toy computer, pick Add, tick Show the three phases, and press Step slowly. Now each press runs one phase, and a new register appears: IR. Watch the outlined cell (where PC points) and the explanation. After four instructions, A holds 28 + 14 = 42 and the output shows it.

Check

The CPU has just fetched the instruction at address 6, which is ADD 14. What's in the program counter while that instruction executes?

7. Fetch copies the instruction into IR and adds 1 to PC straight away, so PC already points at the next instruction during execute. Real CPUs do the same thing, which is why a debugger's "current address" and the program counter can differ by one instruction.

Now edit a program. Every cell's byte is editable: click it and type a new hex value.

In the Add program, change one byte so it outputs 28 − 14 instead of 28 + 14. What should the new byte at address 1 be?

HintAddress 1 holds 2F, ADD 15. Keep the operand and change the opcode.

3F: SUB 15. Type it into cell 1 and press Run, and the output becomes 14. Changing a program and changing data are the same operation, writing bytes.

Jumps make loops and decisions

If PC only ever went up by one, every program would run straight through once and stop. Jumps change that. JMP always sets PC to a new address, which gives you loops. JZ sets it only if the last result was zero, which gives you decisions. Every if, while, and for you write ends up as a few compare-and-jump instructions like these.

Here's the Countdown program next to the Python it does the same job as:

Python

n = 3
while True:
    print(n)
    n = n - 1
    if n == 0:
        break

Toy assembly (address: instruction)

0: LDI 3    ; A = 3
1: OUT      ; print A
2: SUB 15   ; A = A − 1 (address 15 holds 1)
3: JZ 5     ; if A is 0, leave the loop
4: JMP 1    ; otherwise go back to 1
5: HLT

Run Countdown and watch PC jump from 4 back to 1. Only JZ can break the cycle, and only once SUB produces a zero.

Check

In Countdown, you change address 15 from 01 to 02, so the loop subtracts 2 each time. Starting from 3, what happens?

It never stops. A goes 3, 1, then 1 − 2 wraps to 255 (lesson 1's overflow), then 253, 251, and so on. Every value is odd, so it never lands on 0 and JZ never jumps. Try it: the toy computer pauses itself after 500 instructions. A real CPU has no such limit, which is how a program "hangs".

The Multiply program combines both kinds of jump to compute 3 × 4 by adding 3 four times. It keeps a running total at address 13 and a counter at address 15, and it uses STA to write them back each time around the loop.

Practice 4

In the Multiply program, address 14 holds 3 and address 15 holds 4. If you change address 15 to 05 and run it, what number does it output?

HintAddress 15 is the loop counter: how many times 3 gets added.

The loop now adds 3 five times: 15. The CPU has no multiply instruction, so the program builds one out of addition, a counter, and a conditional jump. Early CPUs, like the 6502 in the Apple II, really did multiply this way in software.

From your code to instructions

Real CPUs have the same kind of instructions as the toy one, just more of them and wider. Your code reaches them in one of two ways.

A compiler translates your whole program into machine code before it runs. This is how C, C++, Rust, and Go work. Here's a C function and what GCC turns it into for an x86-64 laptop:

C

int add(int a, int b) {
    return a + b;
}

x86-64 assembly (GCC -O2)

add:
    lea  eax, [rdi+rsi]  ; eax = a + b
    ret                  ; return to caller

Those two lines are 4 bytes of machine code: 8D 04 37 C3. The arguments arrive in registers rdi and rsi, and the result goes back in eax. On an ARM chip, like an Apple M-series Mac or most phones, the same function compiles to add w0, w0, w1 and ret. Different instruction sets, same idea. You can see this for any code at Compiler Explorer, linked below.

An interpreter is a program that reads your code and carries it out. Python does a bit of both: it first compiles your code to bytecode, instructions for an imaginary machine, and then a program called the Python virtual machine runs them. That virtual machine is itself a fetch-decode-execute loop, written in C. You can look at the bytecode with the dis module:

>>> import dis
>>> def add(a, b):
...     return a + b
>>> dis.dis(add)
  1           RESUME                   0
  2           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)
              BINARY_OP                0 (+)
              RETURN_VALUE

That output is from Python 3.14; instruction names change a little between versions. Python's virtual machine keeps values on a stack instead of in named registers: the first instruction pushes a and b, BINARY_OP pops both and pushes their sum, and RETURN_VALUE hands back the top of the stack. Each of those bytecode instructions takes many real CPU instructions to carry out, which is a big part of why Python is slower than C.

Check

When you run a Python script, what actually executes the bytecode instructions?

The Python virtual machine, part of the python program, fetches each bytecode instruction, decodes it, and runs the C code that carries it out. Java and C# work the same way with their own bytecode, but their virtual machines also compile frequently run code to real machine code while the program runs (just-in-time compilation).

What real CPUs add

A modern CPU still fetches, decodes, and executes, but it adds a few big tricks to go faster:

  • More and wider registers. x86-64 has 16 general-purpose 64-bit registers; 64-bit ARM has 31.
  • Pipelining. Like a laundry with a washer and dryer running at once, the CPU fetches the next instruction while decoding one and executing another. Modern cores keep dozens of instructions in flight.
  • Branch prediction. A pipeline needs to know what to fetch next, but a jump's direction isn't known until it executes. So the CPU guesses, usually based on what the jump did last time, and throws the work away if it guessed wrong.
  • Caches. Main memory is slow. A trip to RAM takes on the order of 100 nanoseconds, which is hundreds of clock ticks. So CPUs keep copies of recently used memory in small, fast caches right on the chip.

That last point matters for everyday code. Reading memory in order, like walking through an array, is fast because the cache fetches neighbors ahead of time. Jumping around memory, like following links in a linked list, can be many times slower even when the algorithm looks the same on paper. Stage 4 comes back to this.

Practice 5

A 3 GHz CPU waits 100 nanoseconds for a value from RAM. How many clock ticks is that?

Hint3 GHz is 3 ticks per nanosecond.

3 ticks per nanosecond × 100 ns = 300 ticks. A modern core can finish several instructions per tick, so one slow memory read can cost the time of a thousand instructions. That's why caches exist.

Check

Why does branch prediction exist?

With many instructions in flight, waiting for each jump to finish would stall the pipeline. Guessing keeps the pipeline full; modern predictors are right well over 90% of the time on typical code. When they're wrong, the CPU discards the guessed work and starts over from the right address.

When this goes wrong

The Morris worm, 1988

Because code and data share memory, data can become code. Robert Morris's worm attacked a network service called fingerd, which read a request into a 512-byte buffer without checking its length. The worm sent a longer request containing machine code, which overwrote the function's return address so the CPU jumped into the attacker's bytes. It spread to thousands of machines, a large share of the internet at the time. Modern CPUs and operating systems now mark data memory as non-executable, so the CPU refuses to fetch instructions from it.

Spectre and Meltdown, 2018

Branch prediction made CPUs fast for decades. In January 2018, researchers showed it could leak secrets. When the CPU guesses wrong, it throws away the results, but the guessed work has already pulled data into the cache, and an attacker can measure which memory is now fast to read. That's enough to read passwords and keys from other programs. Fixes went into operating systems, browsers, and new chip designs, and some cost real performance.

What to remember

  • A program is bytes in memory. Whether a byte is code or data depends only on whether the CPU runs it.
  • An instruction is a number: an opcode (what to do) and operands (what to do it with).
  • The CPU loops forever: fetch the instruction at PC and add 1 to PC, decode it, execute it.
  • Jumps overwrite PC. Unconditional jumps make loops; conditional jumps make decisions.
  • Compilers translate to machine code ahead of time. Python compiles to bytecode, and a virtual machine runs it.
  • Memory is hundreds of times slower than the CPU's clock, so caches and access patterns matter.

Try it in Python

The toy computer fits in about fifteen lines of Python. This is the whole fetch-decode-execute loop:

def run(mem):
    pc, a, z = 0, 0, False
    while True:
        ir = mem[pc]; pc = (pc + 1) % 16          # fetch
        op, arg = ir >> 4, ir & 15                # decode
        if   op == 0: return                      # HLT
        elif op == 1: a = mem[arg]                # LDA
        elif op == 2: a = (a + mem[arg]) % 256; z = a == 0   # ADD
        elif op == 3: a = (a - mem[arg]) % 256; z = a == 0   # SUB
        elif op == 4: mem[arg] = a                # STA
        elif op == 5: a = arg                     # LDI
        elif op == 6: pc = arg                    # JMP
        elif op == 7 and z: pc = arg              # JZ
        elif op == 8: print(a)                    # OUT

run([0x53, 0x80, 0x3F, 0x75, 0x61, 0x00] + [0] * 9 + [1])  # Countdown: 3 2 1
