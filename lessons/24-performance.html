Measuring and improving performance

Every lesson in this stage has been about why code runs fast or slow. This last one is about what to do about it: how to measure honestly, how to find the part that matters, and how much speedup is even possible. The answers are often surprising.

Measure first

Programmers are famously bad at guessing where their programs spend time. The slow part is usually somewhere you didn't expect: a quadratic loop buried in a helper, a database call inside a loop, or, as in GTA Online's loading screen, a library function that does far more work than its name suggests. Donald Knuth put it in a 1974 paper:

"We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%."

The second sentence matters as much as the first. The point isn't "never optimize"; it's "find the critical 3% by measuring, then optimize that". Clever code everywhere else just makes the program harder to read and fix.

Check

Users say a web page is slow. What should you do first?

Measure. Very often the answer is a database query or a network call, and no amount of tuning the code you suspected would have helped.

Timing honestly

Measuring sounds easy, but benchmarks lie in predictable ways:

  • Noise. Other programs, power saving, and CPU temperature change the result from run to run. Run many times and look at the spread, not one number.
  • Warm-up. The first run pays for loading code, filling caches, and (in Java or JavaScript) the just-in-time compiler. Time steady-state runs separately.
  • Dead code. If a benchmark computes a result and never uses it, an optimizing compiler may delete the whole computation, and your loop "runs" in zero seconds.
  • Unrealistic data. Sorting already-sorted data, or reading the same small file every time so it's always cached, measures a case your users never hit.

Python's timeit module handles the first two for small snippets: it runs your code many times and turns off garbage collection during the measurement.

Check

A C benchmark of a hash function reports that a billion calls took 0.0 seconds at -O2. What most likely happened?

Dead code elimination. Under the as-if rule from lesson 4, unused work can vanish. Benchmarks fix this by using the results, for example adding them up and printing the total.

Profilers and flame graphs

A profiler tells you where time goes. A sampling profiler, like Linux's perf or Python's py-spy, interrupts the program thousands of times a second and records the call stack each time. Functions that appear in many samples are where the time is spent. Its overhead is low enough to use on production systems. A tracing profiler, like Python's built-in cProfile, records every call: exact counts, but more slowdown.

The standard way to view samples is a flame graph. Each box is a function; boxes stacked on top of it are the functions it called; and a box's width is the share of samples that included it. Wide boxes are where the time goes. Read it from the bottom up, and look for wide plateaus near the top: that's code spending time itself rather than calling something else.

Check

In a flame graph, what does a box's width tell you?

Share of total time, including its callees. The x-axis isn't time order; boxes are sorted so identical stacks merge into wide, readable shapes.

Amdahl's law

In 1967, Gene Amdahl, an IBM computer architect, made a simple point that every performance engineer relies on. If a fraction p of the running time is sped up by a factor s, the overall speedup is:

speedup = 1 / ((1 − p) + p / s)

The (1 − p) part, the time you didn't touch, never shrinks. So even if you make the sped-up part infinitely fast, the best you can do is 1 / (1 − p). Speed up 90% of a program by a factor of 10 and you get about 5.3 times overall, not 10. That's also why adding processors has limits: the part of a job that can't run in parallel caps the benefit of the rest (stage 5 picks this up).

Practice 1

Half of a program's time is spent in one function. If you made that function infinitely fast, what is the best overall speedup?

HintThe other half still takes the same time. 1 / (1 − p) with p = 0.5.

2 times. The untouched half sets the limit, no matter what you do to the other half.

Practice 2

90% of the time is sped up 10 times. What is the overall speedup, to one decimal place?

Hint1 / (0.1 + 0.9 / 10) = 1 / (0.1 + 0.09).

1 / 0.19 ≈ 5.3. Try it on the sliders. Notice the remaining 10% now takes more than half of the new running time: it's become the next thing to profile.

What to try, in order

Once you know where the time goes, the fixes that usually pay off most come in roughly this order:

  1. A better algorithm or data structure (stage 3). Going from O(n²) to O(n log n) can mean a thousand times faster; nothing else on this list comes close.
  2. Avoid the work entirely. Cache results, skip unneeded steps, batch many small database or network calls into one.
  3. Better memory access (lesson 3): arrays over linked structures, data used together stored together.
  4. Let the compiler and libraries help: build with optimizations on, and in Python, push loops into NumPy or other compiled libraries.
  5. Parallelism: multiple cores (stage 5) or vector instructions, within Amdahl's limit.
  6. Micro-optimizations, only in the hottest few lines, and only with a measurement showing they help.

And after every change, measure again. Optimizations often help less than expected, sometimes make things slower, and always make the code harder to change.

Check

A profiler shows 95% of a program's time in a function that checks every pair of 50,000 records for duplicates. Which change is likely to help most?

Change the algorithm. O(n²) to O(n): from about 1.25 billion comparisons to 50,000 set operations. That's the GTA Online fix again. The other options are all real but much smaller wins.

Where this idea comes from

The first flame graph, 2011

Brendan Gregg, a performance engineer then working at Joyent, was investigating a MySQL performance problem and kept getting profiler output that was walls of text: thousands of call stacks, each with a count. Gregg tried drawing them, first with time along the bottom, which was too dense to read, then dropped time order, sorted the stacks so identical ones merged, and colored the boxes in warm tones because they showed which CPUs were "hot". It looked like flames. Gregg released the tool in December 2011, and flame graphs are now built into profilers for nearly every language and into browser developer tools. The lesson behind them is the one this whole lesson argues: you can't fix what you can't see.

What to remember

  • Measure before optimizing. Find the critical 3%; leave the rest readable.
  • Benchmarks lie through noise, warm-up, dead code, and unrealistic data. Repeat runs and use the results.
  • Sampling profilers and flame graphs show where time goes. Wide boxes are what matter.
  • Amdahl's law: overall speedup = 1 / ((1 − p) + p / s). The untouched part sets the limit.
  • Algorithms first, then avoiding work, memory access, compilers and libraries, parallelism, and only then micro-tuning.

Try it in Python

Profile a program with the standard library, sorted by total time:

import cProfile

def slow_unique(items):
    seen = []
    for x in items:
        if x not in seen:          # O(n) scan inside a loop
            seen.append(x)
    return seen

cProfile.run("slow_unique(list(range(20_000)))", sort="cumulative")
# Then swap seen = [] for a set, and run it again.
