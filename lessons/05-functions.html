Functions and abstraction

A function gives a piece of work a name, so you can use it without thinking about how it works. That one idea, used over and over, is how people build programs far too big to hold in their heads. Here you'll see how functions work under the hood, with the call stack, and what makes one well designed.

Watch the call stack

Pick a program and step through it. Each call puts a new frame on top of the stack; each return removes it.

Every running program has a stack like this. When a program crashes, the "traceback" it prints is this stack, written out at the moment things went wrong.

Why functions

Think back over this stage. In lesson 2 you built an adder out of gates, and from then on you could just say "adder" without picturing the XOR and AND gates inside. In lesson 3, the toy CPU used the ALU without caring how it was wired. Each layer hid the one below it behind a simple description of what it does.

That's abstraction: separating what something does from how it does it. Functions are how you build those layers in code. You've already relied on it. You've called print and sorted many times without reading their source, because their interface (the name, the inputs, and what comes back) told you everything you needed.

The payoff is that a function's code, its implementation, can change without breaking anything that calls it, as long as the interface stays the same. When Python's list sorting switched to a new algorithm, Timsort, in Python 2.3 (2003), no one's code had to change.

A function shipping_cost(weight_kg) is used in 40 places. Which change can you make without checking any of those 40 callers?

The faster lookup table. Same inputs, same outputs: only the implementation changed, so callers can't tell. The other three change the interface (the units, the return type, or the parameters), and every caller has to be checked.

Defining and calling

def creates a function. The names in parentheses are its parameters. When you call it, the values you pass in are the arguments, and each parameter is set to its argument. return ends the function and hands a value back to the caller.

def area(width, height):      # width and height are parameters
    return width * height

print(area(3, 4))             # 3 and 4 are arguments; prints 12

Defining a function doesn't run it. Step through "Calls and returns" on the tracer: lines 1 and 4 just create the functions, and nothing inside them runs until line 7 calls sum_of_squares.

Practice 1

What does this print?

def double(x):
    x * 2

print(double(3))
HintThe function computes x * 2. Does it give it back?

None. The function computes 6 and throws it away, because there's no return. A function that reaches its end without a return gives back None. This is one of the most common beginner bugs, and it usually shows up later as an error about NoneType.

Practice 2

With def f(x): return x * x + 1, what does f(f(2)) return?

HintWork from the inside out. The inner call runs first, and its result becomes the outer call's argument.

f(2) is 2 × 2 + 1 = 5, so the outer call is f(5) = 25 + 1 = 26. Arguments are always worked out before the call happens.

Every call gets its own variables

Variables created inside a function are local: they exist only during that call, and no one outside can see them. Parameters are local too. Each call gets a fresh set, stored in a frame, which is exactly what the boxes on the tracer show.

That's what makes functions safe to combine. You can name a variable count inside your function without worrying whether some other code also has a count. Step through "Local scope" and watch two different variables called count, one in each frame.

Practice 3

What does the "Local scope" program print? Predict it before you step to the end.

count = 10

def bump(count):
    count = count + 1
    return count

result = bump(count)
print(count, result)
HintInside bump, count is the parameter, a separate local variable. Which count does line 4 change?

10 11. The parameter count starts out pointing at the same 10, then line 4 moves the local name to 11. The global count never changes. The only way information gets out of bump is its return value. (Python does have a global keyword to change a global from inside a function, but code that relies on it is hard to follow and test.)

The call stack

Function calls nest. sum_of_squares calls square, which might call something else, and every one of them has to return to exactly the right place. The CPU keeps track with the call stack: a pile of frames in memory, one per call that hasn't finished yet.

  • A call pushes a new frame on top, holding the function's local variables and the return address, the spot in the caller to go back to.
  • A return pops the top frame off, hands the return value back, and jumps to the saved return address.

This is the jump from lesson 3, plus memory. On x86-64, the call instruction pushes the return address and jumps; ret, the last line of the compiled add function in lesson 3, pops it and jumps back. Only the top frame is ever running. Everything below it is paused, waiting for a return.

Check

When a function returns, what happens to its local variables?

The frame is popped. The return value goes back to the caller, and the local names disappear. (If a local name pointed at a list that something else also points at, the list itself survives. Only the name is gone.)

Recursion

A function can call itself. That's recursion, and it fits problems that contain smaller copies of themselves. The factorial 4! = 4 × 3 × 2 × 1 is just 4 × 3!, so:

def factorial(n):
    if n == 1:                    # base case: small enough to answer directly
        return 1
    return n * factorial(n - 1)   # recursive case: a smaller copy of the problem

Every recursive function needs both parts. The base case stops the recursion. The recursive case must move toward it. Step through "Recursion" on the tracer and watch the stack grow to its deepest point, then unwind as each frame returns.

Practice 4

At the deepest point of factorial(4), how many factorial frames are on the stack at once?

HintCount the calls that have started but not yet returned when n reaches 1.

4: n = 4, 3, 2, and 1, all waiting at once (plus the global frame under them). factorial(n) uses n frames, so the stack's size grows with the input.

Check

What happens if you call factorial(0) with the code above?

n goes 0, −1, −2, ... and never equals 1, so every call adds another frame. Python stops it at about 1,000 frames (sys.getrecursionlimit()) with a RecursionError. In C, the same bug keeps going until the stack runs out of memory (usually 1 to 8 megabytes by default) and the program crashes with a stack overflow, the error the Q&A site is named after. A safer base case is if n <= 1.

Any recursive function can be rewritten as a loop, and in Python a loop is usually faster and has no depth limit. Recursion earns its place on problems that branch, like walking a folder tree or a family tree, where a loop needs extra bookkeeping. Stage 2 and stage 3 use it a lot.

Passing lists to functions

Remember from lesson 4 that assignment never copies. Calling a function is the same: each parameter becomes a new name for the argument's value. With a number, that never matters. With a list, the function and the caller share one list, so if the function changes it, the caller sees the change. Step through "Shared lists" and follow the arrows: cart and items both point at the same list.

Check

What does this print? (It's a famous Python gotcha.)

def add(x, items=[]):
    items.append(x)
    return items

add(1)
print(add(2))

[1, 2]. A default value is created once, when def runs, not on every call. So every call that leaves out items shares the same list, and it keeps growing. The standard fix:

def add(x, items=None):
    if items is None:
        items = []
    ...

Designing good functions

Writing functions is easy. Choosing where to draw their boundaries is a skill you'll keep improving for your whole career. A few widely shared rules of thumb:

  • One job, with a name that says what it is. If the honest name has "and" in it, like validate_and_save, it's probably two functions.
  • Prefer pure functions. A pure function gives the same output for the same input and changes nothing else: no printing, no global variables, no changing its arguments. Pure functions are easy to test and safe to call anywhere.
  • Say what it promises. A docstring states the interface: what goes in, what comes out, and any conditions. Callers should never need to read the body.
  • Hide the details. A good function has a simple interface over a complicated job. John Ousterhout, whose Stanford course appears in stage 9, calls these "deep modules".
def average(scores):
    """Return the mean of a non-empty list of numbers."""
    return sum(scores) / len(scores)

biggest depends only on its arguments and changes nothing. Real programs need side effects (printing, saving files, reading the clock), so the goal isn't to remove them. It's to keep them in a few clearly named places, with pure logic everywhere else.

One last idea, which stage 2 builds on: in Python, a function is a value like any other. You can store it in a variable or pass it to another function. sorted takes an optional key function and sorts by whatever it returns:

Practice 5

What does sorted(["pear", "fig", "banana"], key=len) return?

Hintlen is called on each word, and the words are sorted by those numbers: 4, 3, 6.

['fig', 'pear', 'banana']: lengths 3, 4, 6. Note that it's key=len, not key=len(). You're handing over the function itself, for sorted to call on each item.

When this goes wrong

The 11 lines that broke the internet, 2016

On March 22, 2016, a developer in a naming dispute unpublished all 273 of his packages from npm, JavaScript's package registry. One was left-pad, a single 11-line function that pads a string with spaces on the left. Thousands of projects depended on it, many without knowing, through packages that depended on packages that depended on it, including the build tools behind React and Babel. Builds failed around the world for a few hours, until npm took the unusual step of restoring the package. npm then changed its rules so that popular packages can't simply be removed. The lesson cuts both ways: reusing functions is the point of abstraction, but every function you depend on is code you've chosen to trust.

What to remember

  • Abstraction separates what something does (its interface) from how (its implementation). Functions are how you build it in code.
  • Parameters are names in the definition; arguments are values in the call. No return means the function returns None.
  • Each call gets a fresh frame of local variables. The only clean way out is the return value.
  • The call stack holds one frame per unfinished call. Calls push; returns pop and jump back.
  • Recursion needs a base case and steps toward it. Too deep, and the stack overflows.
  • Passing a list shares it. Never use a mutable default like items=[].
  • Prefer small, pure, well-named functions with a clear promise.
