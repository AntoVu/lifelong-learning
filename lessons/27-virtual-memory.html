Virtual memory

In stage 4, every process had the same memory layout: code near the bottom, stack near the top. If two processes run at once, how can both have their stack at the same address? Because neither sees real addresses. Every address a program uses is translated, on every single memory access, by hardware the OS controls. This lesson shows how.

Why virtual addresses

Without help, processes sharing one physical memory would get in each other's way: a bug in one could overwrite another, any program could read your browser's passwords, and every program would have to be written to fit wherever there happened to be free memory. Virtual memory fixes all three. Each process gets its own virtual address space, the same clean layout every time, and the hardware translates each virtual address to a physical address the OS has chosen. A process can only reach the physical memory the OS has mapped for it.

Pages and page tables

Translating byte by byte would need an enormous table, so memory is divided into fixed-size blocks: pages in virtual memory and frames in physical memory, usually 4 KB each. An address then splits into two parts: the high bits are the page number, and the low bits are the offset within the page. Translation only changes the page number:

virtual address  = [ page number | offset ]
                        ↓ look up in this process's page table
physical address = [ frame number | offset ]      (offset unchanged)

Each process has a page table mapping its page numbers to frame numbers, with a valid bit and permission bits (readable, writable, executable) per entry. A piece of hardware in the CPU, the memory management unit (MMU), does the lookup on every access. On a context switch, the OS just points the MMU at the next process's page table.

Practice 1

With 4 KB (4,096-byte) pages, how many bits of an address are the offset?

HintThe offset must be able to name every byte in a page: 4,096 = 2 to the what?

4,096 = 2¹², so 12 bits, which is exactly 3 hex digits. That's why page-aligned addresses end in 000 in hex. In the panel's tiny machine, pages are 16 bytes, so the offset is 4 bits: one hex digit.

Practice 3

A 32-bit address space with 4 KB pages has how many pages?

Hint32 address bits minus 12 offset bits leaves the page number.

2²⁰ = 1,048,576 pages. A flat table with one entry per page would be 4 MB per process, mostly unused. So real systems use multi-level page tables, a tree that only stores the parts in use. x86-64 uses four levels (newer chips can use five).

Page faults

If the MMU finds an entry marked invalid, it raises a page fault, which hands control to the OS. That's not necessarily an error. The OS might have set it up that way on purpose:

  • Lazy allocation: when a program asks for a gigabyte, the OS reserves the addresses but only provides a frame when each page is first touched.
  • Swapping: when RAM is full, the OS can write a rarely used page to disk and mark it invalid. Touching it later faults, and the OS reads it back in. If processes keep needing more pages than fit, the system spends all its time moving pages back and forth: thrashing.

If the address isn't one the process is allowed to use at all, the OS ends the process with a segmentation fault. That's what dereferencing a NULL pointer (stage 4) actually triggers: page 0 is deliberately left unmapped so that bug crashes immediately.

Check

A process touches a page that the OS swapped out to disk. What happens?

A page fault the OS handles. The program never notices, except that the access took milliseconds instead of nanoseconds.

The TLB

If every memory access first needed a page table lookup in memory (four of them, with four levels), programs would run several times slower. So the MMU caches recent translations in a small, fast table called the translation lookaside buffer (TLB), usually holding somewhere from dozens to a few thousand entries. Thanks to locality, the same few pages get used over and over, so almost every lookup hits. In the panel, translate several addresses on the same page and watch them hit.

On a context switch, the old process's translations become wrong, so the TLB must be flushed or its entries tagged by process. That's part of why switching processes costs more than switching threads (next lesson).

Check

What does the TLB store?

Translations. It's a cache for the page table, the same caching idea from stage 4 applied to address translation.

What it makes possible

  • Isolation: a process can't touch memory it has no mapping for.
  • Sharing: map the same frame into many processes. Shared libraries (stage 4) are loaded into memory once and mapped read-only into every program that uses them.
  • Copy-on-write: fork (lesson 1) doesn't really copy the parent's memory. It maps the same frames into both processes, marked read-only. Only when one of them writes to a page does the fault handler make a private copy of that page. Since most children call exec right away, most pages are never copied.
  • Memory-mapped files: map a file into memory, and reading a byte of it is just a memory access; page faults load the file on demand.
Check

Why is fork fast even for a process using gigabytes of memory?

Copy-on-write. fork only copies the page tables, and the read-only trick defers the real copying to the moment it's needed, often never.

When this goes wrong

Rowhammer, 2015

Virtual memory's protection rests on one assumption: only the OS can change a page table. In 2014, researchers showed that on many DRAM chips, reading the same row of memory over and over, very fast, could flip bits in the rows next to it, because the cells are packed so tightly that electrical charge leaks between them. In March 2015, Google's Project Zero turned this "rowhammer" effect into an attack. An ordinary program filled memory with page tables, hammered nearby rows until a bit flipped in one of its own page table entries, and gained write access to its own page table, and through that, to all of physical memory. A software protection broken by physics. Memory makers have added defenses since, and the research has continued in both directions.

What to remember

  • Each process uses virtual addresses; the MMU translates them to physical ones using that process's page table.
  • Address = page number + offset. Translation swaps the page number for a frame number; the offset stays.
  • Page faults let the OS allocate lazily and swap to disk. Touching an address you have no right to is a segmentation fault.
  • The TLB caches translations, so most accesses skip the page table walk.
  • Virtual memory enables isolation, shared libraries, copy-on-write fork, and memory-mapped files.

Try it in Python

Map a file into memory and read it like a byte array:

import mmap

with open("data.bin", "wb") as f:
    f.write(b"hello, virtual memory")

with open("data.bin", "rb") as f, mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as m:
    print(m[:5])           # b'hello' : the page was loaded on first touch
    print(mmap.PAGESIZE)   # 4096 on most systems
