File systems

A disk only knows numbered blocks of bytes. Yet you see folders, file names, and documents that survive a power cut. The file system is the layer that turns one into the other, and its hardest job is surprisingly specific: making sure a crash at the worst possible moment doesn't leave a mess.

Pull the plug

Appending one block to a file takes three separate writes to the disk. Click "Crash before this" on any step to cut the power just before it, and see what state the disk is left in. Then turn on journaling.

    Without a journal, a crash between the inode write and the bitmap write leaves a file pointing at a block the system thinks is free, which will later be handed to another file. And disks are allowed to reorder writes, so other orders are possible too, each with its own kind of damage: an inode pointing at garbage, or a block marked used that nothing points to. With journaling, every crash point recovers to either the old state or the new one, never something in between.

    Files, inodes, and directories

    To a Unix file system, a file is just an array of bytes plus some facts about it: its size, owner, permissions, timestamps, and where its bytes are stored. Those facts live in a record called an inode, identified by a number. Notice what's missing: the file's name.

    Names live in directories. A directory is a special file whose contents are a list of (name, inode number) pairs. To open /home/ada/notes.txt, the OS starts at the root directory's inode, which it knows, reads that directory to find home's inode number, reads home to find ada, reads ada to find notes.txt, and finally reaches the file's inode. Recently used directories and inodes stay cached in memory, so this is usually fast.

    Because names just point to inodes, one file can have several names: a hard link. The inode counts its links, and the file's data is only freed when the count reaches zero and no program has it open. That's why the Unix call to delete a file is named unlink.

    Practice 1

    Opening /home/ada/notes.txt, how many directories does the OS read to find the file's inode?

    HintEvery directory on the path is read, starting with the root.

    3: /, home, and ada. Deeply nested paths cost more lookups, which is one reason the OS caches directory entries aggressively.

    Check

    A file has two hard links. You delete one name. What happens to the file's data?

    Nothing happens to the data. It's freed only when the last link is gone. The Python example at the end of this lesson shows it.

    On the disk

    A typical Unix file system divides the disk into fixed-size blocks, usually 4 KB, and reserves some for bookkeeping: a superblock describing the whole file system, bitmaps marking which inodes and data blocks are in use, the inode table, and then the data blocks themselves.

    An inode records where its file's data is with a list of block pointers. A few are direct, each pointing at a data block. For bigger files, an indirect pointer points at a block full of more pointers, and a double-indirect pointer at a block of those. Small files, which are most files, need only the direct pointers; huge files are still possible. (Newer file systems like ext4 describe large files with extents, "blocks 5,000 to 9,000", instead of one pointer per block.)

    Practice 2

    An inode has 12 direct pointers, and blocks are 4 KB. How many KB can a file hold using only direct pointers?

    HintOne block per pointer.

    12 × 4 KB = 48 KB. That's the classic Unix design, still used by ext2 and ext3, and it covers most files on a typical system.

    Practice 3

    A single indirect block is 4 KB and holds 4-byte block pointers. How many pointers fit in it?

    Hint4,096 bytes divided by 4 bytes each.

    1,024 pointers, so one indirect pointer adds 1,024 × 4 KB = 4 MB of file. A double-indirect block adds 1,024 times that again: 4 GB.

    Crash consistency and journaling

    Growing a file by one block means updating three places: the data block itself, the inode (new size and pointer), and the data bitmap (mark the block used). The disk can only write one at a time, and power can fail between any two. The panel shows what each partial state means. The old fix was a program called fsck that scanned the whole disk after a crash to find and repair inconsistencies, which took hours on large disks.

    Modern file systems use journaling, an idea borrowed from databases (stage 7). Before touching the real locations, write a description of all the changes to a separate area, the journal, and then write a small "commit" record. Only after the commit is safely on disk are the real locations updated. After a crash, the OS checks the journal: a committed transaction is replayed; an uncommitted one is ignored. Either way, the update happened completely or not at all. ext4, NTFS, and XFS journal; Apple's APFS and Linux's Btrfs get the same guarantee differently, by never overwriting data in place (copy-on-write, from lesson 3).

    Check

    Power fails after a journaled transaction is written to the journal but before its commit record. What does recovery do?

    Ignore it. The update is lost, but nothing is corrupted. The commit record is the single point where the update becomes official.

    When is data really saved?

    When write() returns, your data is usually only in the OS's page cache in memory, which will be written to disk in a few seconds. That's much faster, and it's why a power cut can lose recent writes. Programs that must not lose data call fsync(), which doesn't return until the file's data is on the disk itself. Databases call it every time they promise a transaction is saved; text editors call it when you save. It's slow, so programs batch work between calls.

    Disks add their own layers: drives have caches too, and SSDs store data in flash cells that wear out, so their firmware spreads writes around and moves data behind the scenes. File systems and drives have to cooperate carefully for fsync to mean what it says.

    Check

    Your program calls write(), it returns successfully, and a second later the power fails. Is the data safe?

    Not guaranteed. Journaling keeps the file system consistent, but consistent can mean "without your last second of writes". If losing it matters, call fsync.

    When this goes wrong

    fsyncgate, 2018

    PostgreSQL, one of the most trusted databases, relied on a reasonable assumption: if fsync() fails, perhaps because of a disk error, you can call it again later, and when it succeeds your data is on disk. In 2018, its developers discovered that on Linux this wasn't true. When writing back cached data failed, Linux reported the error once and then marked those pages clean, so the next fsync() returned success even though the data had never reached the disk. Data could be lost while every check passed. After long discussions between database and kernel developers, PostgreSQL changed course: since then it treats any fsync failure as fatal, stops, and recovers from its own log, a fix it also applied to its older supported versions. Even the most basic promise, "this is saved", depends on every layer agreeing what it means.

    What to remember

    • A file is an inode (metadata and block pointers) plus data blocks. Directories map names to inode numbers.
    • Paths are looked up one directory at a time. Hard links are extra names for one inode.
    • The disk holds a superblock, bitmaps, an inode table, and data blocks. Indirect pointers let small inodes describe huge files.
    • One logical update takes several writes; journaling makes it all-or-nothing after a crash.
    • write puts data in a cache; fsync puts it on the disk.

    Try it in Python

    Hard links and fsync (Linux or macOS):

    import os

with open("notes.txt", "w") as f:
    f.write("hello")
    f.flush()
    os.fsync(f.fileno())          # don't return until it's really on disk

os.link("notes.txt", "also-notes.txt")      # a second name for the same inode
a, b = os.stat("notes.txt"), os.stat("also-notes.txt")
print(a.st_ino == b.st_ino, a.st_nlink)     # True 2
os.remove("notes.txt")
print(open("also-notes.txt").read())        # hello: the data is still there
os.remove("also-notes.txt")
