From source code to running program

You type gcc main.c util.c -o app and get a program. Behind that one command are four separate tools and a fifth step when you run it. Knowing them turns baffling errors like "undefined reference" into one-line fixes, and explains how libraries, updates, and some famous attacks work.

One program through the pipeline

Click each stage to see what it produces for this two-file program. Outputs come from GCC and GNU binutils, trimmed and shown as they look on Linux; the Link step is summarized.
util.h
#define SQUARE_LIMIT 100
int square(int x);
util.c
#include "util.h"

int calls = 0;

int square(int x) {
    calls++;
    return x * x;
}
main.c
#include <stdio.h>
#include "util.h"

int main(void) {
    int y = square(7);
    if (y < SQUARE_LIMIT)
        printf("%d\n", y);
    return 0;
}

Each stage is a separate program that the gcc command runs for you in order. Run gcc -v main.c util.c and you'll see every one of them being called, with all its options.

The preprocessor

Before the compiler sees your code, the preprocessor rewrites it as plain text. #include pastes in the whole contents of another file. #define sets up a text substitution: every SQUARE_LIMIT becomes 100. Lines like #ifdef keep or drop code depending on settings, which is how one source file builds for both Windows and Linux.

Text substitution knows nothing about C, which leads to a classic trap:

#define DOUBLE(x) x + x

int n = DOUBLE(3) * 2;     // becomes: 3 + 3 * 2, which is 9, not 12

The fix is parentheses everywhere, #define DOUBLE(x) ((x) + (x)), or better, an ordinary function, which modern compilers inline anyway.

Practice 1

With #define SQUARE(x) x * x, what is SQUARE(1 + 2)?

HintPaste the text in literally: x becomes 1 + 2 in both places. Then apply normal precedence.

It becomes 1 + 2 * 1 + 2, and multiplication goes first: 1 + 2 + 2 = 5, not 9. With #define SQUARE(x) ((x) * (x)) it would be ((1 + 2) * (1 + 2)) = 9.

Separate compilation

Each .c file is compiled on its own, with no knowledge of the others. So how does main.c call square, which lives in util.c? Through a declaration in the header: int square(int x); tells the compiler the function exists and what types it takes, without saying how it works. The definition, the body, appears in exactly one .c file.

The compiler turns each file into an object file (.o): machine code with blanks where it needs things from elsewhere, plus a table of symbols, the names it defines and the names it needs. nm lists them: T means a function defined here, B a global variable defined here, and U an undefined name someone else must supply.

Separate compilation is what makes big projects practical. Change one file and only that file is recompiled; build tools like make track which outputs are out of date. Linux has tens of thousands of .c files, and nobody recompiles them all to fix one line.

Check

In nm main.o, square is listed with a U. What does that mean?

Undefined here, needed from elsewhere. In util.o, the same name appears with a T: defined in the text (code) section. The linker's job is to match every U with exactly one definition.

The linker

The linker (ld) combines object files into one executable. It matches every undefined symbol to its definition, lays out all the code and data at final addresses, and fills in the blanks with those addresses (relocation). Two errors come straight from that job. Try them:

"Undefined reference" means nothing you gave the linker defines that name: usually a missing file or library on the command line (or a typo). "Multiple definition" means two files define the same name; often a function body was put in a header that two files include.

Check

A build fails with undefined reference to `sqrt', though the code includes <math.h>. What's the likely fix?

The header only declares sqrt; the definition lives in the math library, which on Linux you link with -lm. Compiler errors are about declarations and types; linker errors are about missing or duplicate definitions.

Static and dynamic libraries

A library is a bundle of object files. With static linking (.a on Linux, .lib on Windows), the linker copies the needed code into your executable. The program is self-contained but bigger, and fixing a bug in the library means rebuilding every program that used it.

With dynamic linking (.so on Linux, .dll on Windows, .dylib on macOS), the executable only records the library's name. The code is found and connected when the program starts. Every program on the machine shares one copy in memory, and one update to the library fixes all of them at once. The cost: the program depends on the right version being installed, the old Windows complaint known as "DLL hell". printf in our example comes from the C standard library, which is almost always linked dynamically.

Check

A security flaw is found in a widely used compression library. Which programs get the fix just by updating the library's file on the system?

Dynamically linked programs, after a restart. Statically linked ones keep the vulnerable copy until they're rebuilt. That's a big reason Linux distributions prefer dynamic linking, and it cuts both ways, as the story below shows.

The loader

When you run a program, the operating system's loader reads the executable file (ELF format on Linux, PE on Windows, Mach-O on macOS), maps its code and data into a new process's memory (the layout from lesson 2), and hands off to the dynamic linker to find and connect the shared libraries. Then it jumps to the program's entry point, a small startup routine called _start that sets up the C runtime and calls your main. When main returns, that routine passes your return value back to the operating system as the exit code.

Other languages shift these steps around. Java compiles to bytecode in .class files and links classes as they're first used, while running. Python compiles each module to bytecode (cached in .pyc files) when it's imported. Go and Rust link almost everything statically into a single executable, which is a big part of why they're easy to deploy.

When this goes wrong

The XZ Utils backdoor, 2024

On March 29, 2024, a Microsoft engineer, Andres Freund, noticed that SSH logins on a test machine were taking about half a second longer than usual and using too much CPU. He traced it to liblzma, a compression library from the XZ Utils project. Over two years, someone using the name "Jia Tan" had become a trusted maintainer of the project and hidden a backdoor in its build files and test data. The SSH server never used compression itself, but on several Linux distributions it was dynamically linked against a system library that loaded liblzma, and the malicious code used the dynamic linker's startup process to hook SSH's authentication. The backdoored versions had only reached testing and early releases, so the major stable releases were never affected. Dynamic linking spreads fixes instantly; it can spread compromises too.

What to remember

  • Building C runs four stages: preprocess (text substitution), compile (to assembly), assemble (to object files), link (to an executable).
  • Macros are text; parenthesize them, or use functions.
  • Headers hold declarations; one .c file holds each definition. Object files list defined (T, B) and undefined (U) symbols.
  • "Undefined reference": a definition is missing from the link. "Multiple definition": there are two.
  • Static linking copies library code in; dynamic linking connects shared libraries at startup. The loader maps the program and calls main.

Try it yourself

gcc -E main.c | tail          # see the preprocessed text (SQUARE_LIMIT is gone)
gcc -S main.c                 # main.s: assembly
gcc -c main.c util.c          # main.o and util.o: object files
nm main.o util.o              # their symbols
gcc main.o util.o -o app      # link
ldd ./app                     # Linux: the shared libraries it will load
