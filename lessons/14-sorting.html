Sorting

Sorting is the most studied problem in computer science, and for good reason: sorted data makes searching, removing duplicates, grouping, and merging easy. This lesson compares four ways to sort, and shows why the good ones can't beat O(n log n).

The simple sorts

Selection sort is how many people sort by hand: find the smallest item and put it first, then find the smallest of the rest and put it second, and so on. Finding each minimum scans everything left, so it always takes about n²/2 comparisons, even if the input was already sorted.

Insertion sort is how people sort a hand of cards: take each new item and slide it left past the bigger ones until it's in place. On random input it's also O(n²). But on nearly sorted input each item only slides a little, so it approaches O(n). That makes it the best choice for small or nearly sorted lists, and real libraries use it for short runs inside faster algorithms.

def insertion_sort(xs):
    for i in range(1, len(xs)):
        j = i
        while j > 0 and xs[j - 1] > xs[j]:
            xs[j - 1], xs[j] = xs[j], xs[j - 1]   # slide left
            j -= 1
Practice 1

How many comparisons does insertion sort make on a list of 10 items that's already sorted?

HintEach item from the second onward compares once with its left neighbor, finds it smaller, and stops.

9, one per item after the first: n − 1. The same list reversed takes 45 (every item slides all the way). Best case O(n), worst case O(n²).

Merge sort

The fast sorts use divide and conquer, the recursion idea from stage 2. Merge sort splits the list in half, sorts each half recursively, then merges the two sorted halves by repeatedly taking the smaller front item:

def merge_sort(xs):
    if len(xs) <= 1:
        return xs                                   # base case: already sorted
    mid = len(xs) // 2
    left, right = merge_sort(xs[:mid]), merge_sort(xs[mid:])   # leap of faith
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):        # merge: O(n)
        if left[i] <= right[j]:
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

Why O(n log n)? Halving n until the pieces have one item takes log₂ n levels. At every level, the merges together touch all n items once. So the total is n work per level × log n levels. Unlike quicksort, merge sort is O(n log n) on every input; the price is extra memory for the merged output.

Practice 2

Merge sort on 8 items: how many levels of merging are there?

HintMerges of 1+1 items, then 2+2, then...

3: pairs into 2s, 2s into 4s, 4s into 8. That's log₂ 8. Each level does about 8 units of merging, so roughly 8 × 3 = 24 steps in total.

Quicksort

Quicksort divides differently. It picks one item, the pivot, and partitions the list so everything smaller is on its left and everything larger on its right. The pivot is now in its final place, and quicksort sorts the two sides recursively. No merging needed, and it sorts in place, which makes it very fast in practice.

Its speed depends on the pivot. If the pivot lands near the middle, each split halves the problem and the total is O(n log n). The version in the panel uses the last item as the pivot. On already sorted input, that's always the largest item, so every partition peels off just one item, and the total becomes n + (n − 1) + ... + 1: O(n²). Real implementations avoid this by choosing the pivot randomly, or as the median of a few samples.

Practice 3

Quicksort with the last item as pivot runs on the already sorted list [1, 2, 3, 4, 5]. How many comparisons does it make in total?

HintThe first partition compares the 4 other items with the pivot 5, and leaves [1, 2, 3, 4] to sort.

4 + 3 + 2 + 1 = 10, which is n(n − 1)/2. The worst case is exactly selection sort's count. Try "Already sorted" with quicksort in the panel at 32 items: 496 comparisons.

Check

What makes quicksort hit its O(n²) worst case?

Unbalanced splits. A split of n into 0 and n − 1 makes no real progress. Random pivots make that astronomically unlikely, which is why quicksort's expected time is O(n log n) on any input.

The speed limit

Could a cleverer algorithm sort in O(n)? Not if it only learns about the data by comparing pairs. Here's the argument. A list of n distinct items can be in n! different orders, and the sort must tell them all apart. Each comparison has two outcomes, so k comparisons can distinguish at most 2ᵏ orders. You need 2ᵏ ≥ n!, so k ≥ log₂(n!), which works out to about n log₂ n. Every comparison sort needs Ω(n log n) comparisons in the worst case; merge sort is as good as it gets.

(Sorts that don't compare can beat it on special data. Counting sort puts small integers straight into buckets by value in O(n), for example. But for arbitrary items, n log n is the limit.)

Practice 4

What's the smallest number of comparisons that can sort any list of 3 distinct items?

Hint3 items have 3! = 6 possible orders. How many yes-or-no answers do you need to tell 6 things apart?

Two comparisons give at most 4 outcomes, which isn't enough for 6 orders. You need 3, and 3 is enough.

Sorting in Python

In real code, call sorted(xs) (returns a new list) or xs.sort() (sorts in place). Both use Timsort, which Tim Peters wrote for Python in 2002. It finds runs that are already in order, extends short ones with insertion sort, and merges them like merge sort. That makes it O(n log n) in the worst case and close to O(n) on data that's nearly sorted, which real data often is. Java, Android, and V8 (Chrome's JavaScript engine) adopted it too.

Timsort is stable: items that compare equal keep their original order. That lets you sort by several things in steps, and it makes key functions predictable:

people = [("Ada", 36), ("Grace", 85), ("Alan", 41), ("Linus", 36)]
sorted(people, key=lambda p: p[1])
# [('Ada', 36), ('Linus', 36), ('Alan', 41), ('Grace', 85)]
#   Ada and Linus tie at 36 and stay in their original order
Practice 5

What does sorted(["bb", "a", "cc", "d"], key=len) return?

HintSort by length. Among items with equal length, a stable sort keeps the original order.

['a', 'd', 'bb', 'cc']. The one-letter strings come first in their original order (a before d), then the two-letter ones (bb before cc).

Check

A log file is sorted by time, but a few late entries are slightly out of place. Which sort handles it fastest?

Both are adaptive: they do less work on nearly sorted data, approaching O(n). Timsort was designed around this case, because real data is so often partly ordered.

When this goes wrong

The bug in Timsort, 2015

Timsort had run in Python since 2002 and in Java since 2011, sorting data on billions of devices. In 2015, researchers in the EU's ENVISAGE project tried to formally prove Java's version correct using a verification tool called KeY. The proof failed. Timsort keeps a small stack of runs waiting to be merged, sized in advance based on a rule about run lengths, and the code only checked that rule for the top three runs. The researchers constructed inputs that broke the rule deeper in the stack, which made Java's sort crash with an out-of-bounds error. The smallest such input was 67,108,864 items, so no test suite had found it. Python, Java, and Android all shipped fixes. Testing shows a bug is present; only proof shows one is absent.

What to remember

  • Selection sort is always O(n²). Insertion sort is O(n²) but O(n) on nearly sorted data.
  • Merge sort: split, sort halves, merge. O(n log n) always, with extra memory.
  • Quicksort: partition around a pivot. O(n log n) on average, O(n²) with bad pivots; pick them randomly.
  • Comparison sorts can't beat Ω(n log n): there are n! orders to tell apart.
  • Use sorted with key=. It's Timsort: stable and fast on partly sorted data.

Try it in Python

import random, timeit

xs = [random.random() for _ in range(5_000)]

def insertion_sort(a):
    a = a[:]
    for i in range(1, len(a)):
        j = i
        while j > 0 and a[j - 1] > a[j]:
            a[j - 1], a[j] = a[j], a[j - 1]
            j -= 1
    return a

print(timeit.timeit(lambda: insertion_sort(xs), number=1))   # seconds
print(timeit.timeit(lambda: sorted(xs), number=1))           # around a millisecond
